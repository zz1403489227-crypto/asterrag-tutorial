# 第 34 章：从监控到评测闭环——让一次排查变成持续改进

第 32 章让一次执行可见，第 33 章让一条问题可解释。这一章把视角放大：很多请求一起运行时，怎样发现异常、保留重要样本，再把它们变成下一轮评测？

仍然只讨论理想方案，不把示意阈值或样本数量当作实测结果。目标不是背监控产品名，而是讲通这条循环：

```text
真实请求或离线评测执行
  → 指标发现异常 / 用户反馈 / 定向抽查
  → 关联 Trace、日志与实际输入输出
  → 诊断并归类问题
  → 脱敏、去重、补标准，形成评测候选
  → 在固定样本上比较改动
  → 通过验收后再考虑发布，并持续观察
```

这里有两种不同节奏：监控尽快发现“出事了没有”，评测较慢地判断“是否真的更好”。它们相互提供线索，但不能相互替代。

## 34.1 第一件事：不要把所有成败揉成一个成功率

至少要分开四个问题：

| 层次 | 问的是什么 | 典型观察 |
|---|---|---|
| 执行可用性 | 请求有没有正常完成 | 超时、异常、取消、工具业务失败 |
| 任务质量 | 用户目标是否达成 | 参数是否答全答对，业务操作是否真实完成 |
| 效率与成本 | 为了达成目标付出了什么 | 首字时间、总时长、模型轮数、工具次数、token 用量 |
| 评测自身健康 | 答卷和分数是否可信地生成 | 录制缺失、裁判失败、参考缺失、指标不适用 |

例如某题模型服务超时、某题正常回答但参数错、某题回答正确但裁判限流，这三件事不应该都叫“模型准确率下降”。

同样，工具 HTTP 请求成功不等于工具业务成功；工具业务成功不等于 Agent 最终任务成功。指标应该和明确的验收条件对应，而不是沿用某一个底层 `success` 字段覆盖所有层次。

## 34.2 把分母说清楚，比多报十个指标更有用

假设一批计划执行 100 道题，实际情况如下，数字仅用于说明：

- 100 道都发起了作答；90 道拿到完整答卷，10 道执行超时。
- 90 份答卷都应评分；其中 85 份成功判分，5 份裁判失败。
- 在成功判分的 85 份里，68 份达到本次质量标准。

那么：

```text
答卷完成率      = 90 / 100 = 90%
判分覆盖率      = 85 / 90  ≈ 94.4%
已判分质量通过率 = 68 / 85  = 80%
全批已确认通过比例 = 68 / 100 = 68%
```

最后一个数字同时受执行、判分覆盖和质量影响，不能冒充纯答案质量；80% 则只描述有有效评分的子集，也不能掩盖那 15 道未确认通过的题。

这是一种报表设计口径，不是官方评测器已经采用的统一公式。若某指标只适用于需要检索的题，它还应使用自己的适用样本分母。裁判失败、数据缺失、不适用与真的得零分分别记录。

没有完成的请求也要纳入执行状态统计。只画成功请求的平均延迟，可能出现“最慢的都超时被排除了，平均延迟反而变好”的假象。超时与取消比例应并列展示；其实际结束时间或截止时间的统计口径要明确，不能假装已知完整生成耗时。

## 34.3 面向 Agent / RAG，优先看哪些指标

沿着用户体验和决策过程选，不必先做一个塞满 CPU、Redis 和消息队列的看板。

**第一组：有没有顺利完成。** 看请求异常、超时、取消、工具业务失败和结果未知。按模型、工具、版本和场景拆分，才能知道问题集中在哪里。

**第二组：等待是否合理。** 看首个用户可见内容时间、总完成时间、模型和工具耗时分布。平均值描述总体水平，p95 描述较慢尾部：约 95% 的观测值不超过该位置，具体取值依赖所用分位数算法。小样本的 p95 会很不稳定，必须同时展示样本量。

**第三组：有没有完成正确的事情。** 离线看前文的检索与答案指标；Agent 另看工具选择/参数、任务完成、必要步骤和权限约束。线上无标准答案时，用户反馈、引用检查和抽样裁判先当质量线索，不能直接等同真实准确率。

**第四组：过程是否浪费。** 看模型轮数、工具调用次数、重复调用、重试、输入输出 token、预算触顶。工具次数少不自动更好：少查一次可能更快，也可能遗漏证据。要在任务达成条件下比较效率。

成本可以按模型、调用时适用的计费规则和实际用量估算，保留估算口径；无法获得用量时记为未知，不填零。离线裁判也消耗模型调用，最好与被评系统成本分开。

图检索等可选通道的“未启用”，应与“启用了却返回空”区分。否则看板会把配置差异当成故障。

## 34.4 告警不是每出现一行 ERROR 就通知人

好的告警至少说清四件事：发生了什么、影响多少请求、从何时开始、应该先查哪里。

可以先按严重程度分两类：

- **快速处理的运行问题**：大量请求失败、工具持续不可用、成本失控，或者出现越权外部操作等高风险事件。
- **需要复核的质量变化**：某类参数题低分增多、图谱多跳题退化、重复调用比例上升。质量信号往往有延迟和裁判噪声，先关联代表案例再判断。

假设业务目标是“绝大部分参数问答能及时完成”。一种教学告警可以写成：连续若干时间窗内、请求数达到最低要求后，超时比例持续超过目标线，再按版本分组触发。具体窗长、请求量和阈值必须来自服务目标及基线，不能通用地拍一个数。

为何不一次超时就报？因为短暂抖动会造成告警噪声。但低流量并不等于可以完全忽略故障：低流量服务可结合探测请求、连续失败或单次严重事件，而不是永远等不到最低样本量。

告警内容最好带：指标与分母、受影响场景和版本、起止时段、可授权查看的 Trace 示例、近期配置变化、建议检查步骤。恢复后也应收敛通知；同一故障引起的多条告警应尽量归并。

告警负责召集注意力，不代表已经确认根因。比如发现模型超时集中于某版本，仍需要回到第 33 章检查输入长度、排队、重试与外部服务情况。

## 34.5 把问题接回评测：为什么随机抽样不够

设想每天有很多参数咨询，大部分很简单。只随机抽 100 道，得到的很可能仍是“大多数常见问题”。这适合了解常见流量，却不保证覆盖跨文档、型号歧义、工具重试、权限边界等低频但重要的难点。

反过来，只挑最差案例组成 100 道题，又会高估日常问题比例。于是应分开两个用途：

| 集合 | 怎样选 | 用来回答什么 |
|---|---|---|
| 代表性集合 | 按主要场景分层，保留或明确还原流量权重 | 常见业务整体表现如何 |
| 难例与风险集合 | 按失败机制、严重性、新场景定向补充 | 已知薄弱点和重要边界改善了吗 |
| 冻结保留集 | 与调优样本隔离，稳定版本与访问规则 | 改动是否只适应了反复看过的题 |

保留集可以从前两类分层划出，不必理解成与它们毫无关系的第三种业务分布。它强调的是**是否参与调优**这一边界。

如果难例集中含有很多重复调用案例，报告“难例通过率”即可，不应不加权地称为全站任务成功率。代表性集合若对少数场景过采样，也要按目标分布加权或分别报告。

## 34.6 从一条线上记录变成一道好评测题，需要做什么

仍以“14 Pro 参数答错”为例，不能只把那句问题复制进表格。一个可用案例应逐步加工：

1. **确认使用范围并脱敏**：只保留该题必要输入；删除身份、凭据与无关聊天内容，处理私有文档权限。
2. **恢复任务上下文**：这句是否依赖上一轮“请比较这两款”？若依赖，多轮上下文属于输入，不能删掉后继续用原答案做标准。
3. **归类机制**：型号消歧、事实遗漏、检索范围错误、工具结果未回填等。现象与原因标签分开，原因未确认时留待复核。
4. **去重但保留有效变化**：“14 Pro 屏幕多大”与近义问法可分组；普通版与 Pro、单轮与依赖历史则可能是关键差异，不应机械去重。
5. **补充可验收标准**：在确定的资料版本下，应答哪些事实、哪些文档可支持、允许哪些表达、何时应澄清或拒答。
6. **人工检查与划分**：检查输入是否充分、参考是否正确，将高度相关的样本成组划分，避免同一模板改几个字就同时进入调优集和保留集。
7. **版本化**：保存题目版本、参考版本、适用范围、来源追溯的受控引用和加入原因，再进入离线评测。

比如一条失败来自长期记忆污染，离线样本中却不给任何记忆初始状态，运行后问题不再出现。这不是系统被修好了，而是案例没有保留触发条件。

实时价格、库存和订单状态还需要时间或受控工具状态。否则昨天正确的答案今天失效，分数变化可能只是世界变了。

原始观测数据可以保留在权限控制的存储中，评估集只带必要且获准使用的内容。不能把“做评测”当成把用户数据随意送给外部模型裁判的理由。

## 34.7 没有标准答案，能不能先评

能，但必须知道评到了什么。

例如模型说“屏幕为 6.73 英寸”，材料也这样写。无需另一份参考答案，就可以检查这句话是否被材料支持；还可以看引用是否可定位、工具参数是否符合 schema、是否超时、是否超过调用预算。

然而这并不能证明材料本身正确，也不能证明用户要求的刷新率已经回答完整。忠实于材料、回答切题与客观事实正确，是不同维度。

没有真值时，可以先做规则检查、抽样模型审查、用户反馈归类和新旧答案盲评，筛出值得复核的样本。把裁判偏好当弱信号，不把它直接升级为金标准；优先给高风险、高争议、反复失败的样本补人工参考。

当两个裁判意见不一致时，保留判定依据，核对参考与验收规则，必要时交给熟悉业务的人裁决。不能只多投几次票，就假定共同错误会消失。

## 34.8 线上数据很多，Trace 要不要全部存

先区分“用于总体计数的指标”和“用于详细诊断的 Trace”。理想上总体请求计数等指标不应只来自偏向错误案例的 Trace 子集；否则你保留了更多失败样本，就会算出一个虚高的失败率。

规模受控的离线评测可以尽量完整保留每题关键轨迹，同时设置单条大小和敏感字段限制。大量线上流量则可以保留一部分正常样本，并优先保留异常、慢请求或指定实验版本。

追踪采样有两个常见位置：请求开始就决定是否记录，是头部采样；收集到较完整过程后再按错误、耗时等决定保留，是尾部采样。前者便宜但事先不知道最终是否失败，后者能利用结果但需要缓冲和处理容量。两者基础概念见 [OpenTelemetry 采样说明](https://opentelemetry.io/docs/concepts/sampling/)。

已经在前面丢掉的 Trace，后面的尾部采样无法凭空补回。最终是否保留完整过程，还受迟到事件、缓冲上限和采集失败影响，不能口头保证“所有错误永远都有完整 Trace”。

日志和快照还可以按字段、事件种类及保留期限控制成本。评测只需关键阶段材料时，不必永久保存每个流式 token 事件。Trace ID、用户 ID 等高基数字段适合查询单例，不宜直接当作每个监控指标的标签，以免产生海量序列；看板优先使用场景、版本、工具等规模受控的维度。

## 34.9 观测系统也会失败，而且不能成为泄密渠道

设计上可分两层保存：普通日志保留脱敏摘要、状态和引用；授权诊断存储按需要保留完整输入输出。设置访问权限、期限与删除策略，密钥和认证头不进入这两层。给内容做哈希不等于完成脱敏，尤其当原文很容易枚举时。

采集写入不要无界阻塞用户回答：可以批量异步发送、限制队列和大小、监控丢弃数量与导出失败。但“异步”并不等于可靠，丢失时应显示观测不完整；有强审计要求的高风险操作，需要另外定义持久化与准入保证，不能简单沿用尽力而为的诊断日志。

这与源码学习的联系是：项目已有对部分 Trace 写入异常记录警告的处理，体现了观测不应轻易破坏回答路径的考虑。扩展设计还需要回答队列满、采集失败和隐私保留的问题，而不是只把记录字段越加越多。

## 34.10 最后怎样闭环，而不是“看完日志就结束”

假设前面的诊断怀疑“改写丢掉型号限定”。完整的改进提案可以是：

1. 把该案例及适当变体归入型号消歧问题，补充参考与资料版本。
2. 在调优集上修改改写约束，记录代码/提示版本；其它重要条件固定。
3. 比较相同题的答案质量、实际材料、延迟与成本，检查改善是否符合预期机制。
4. 用未参与调优的样本检查是否影响其他场景，避免修好 Pro 问题却破坏上下文指代。
5. 若将来部署，在明确的验收和回退条件下逐步发布，观察线上指标与新案例。

步骤是未来方案，不是本轮执行记录。改进是否有效仍然是待验证结论。

这里最有价值的产物不只是一个更高的分数，而是可解释的对应关系：**发现了哪类问题，依据什么判断，改了什么，用哪些固定样本检查，又承担了什么成本。**

## 34.11 把题库里的追问归纳成一段面试回答

> 如果由我设计评测观测体系，我会先分开执行可用性、答案质量、效率成本和评测器自身健康。用指标发现异常，按批次、题目和作答尝试定位 Trace，再看结构化日志与实际上下文。线上案例不是直接随机复制成评估集，而是先脱敏、恢复必要状态、归类去重、补验收标准，分成代表性样本和定向难例，并隔离调优集与保留集。对无真值案例先做规则和弱信号筛查，重要案例再补人工参考。这样评测结果可以追到过程，过程问题又可以沉淀为回归案例。

若追问“这些你真实做过吗”，直接回答范围：本教程支持的是对现有实现的研究和扩展方案设计，没有真实运行评测或生产监控。无需虚构分数、工具部署经历或故障恢复故事，也能把方案讲完整。

这三章补上的，就是评测分数之后的那条主线：**结果可见 → 过程可查 → 原因可解释 → 改进可比较。**
