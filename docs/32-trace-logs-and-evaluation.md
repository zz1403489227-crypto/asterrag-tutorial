# 第 32 章：Trace、日志与指标——给一次回答留下能解释的过程

前六章已经解释了怎样出题、录制、评分。但当面试官追问“有一道题分数很低，你怎么知道哪里出了问题”，仅说“看日志”还不够。

这一章先把“看什么”讲清楚，下一章用它排错，最后一章把排错接回监控和评测。第 32～34 章统一讨论**理想设计方案**：不用启动项目，文中的轨迹、字段和数字是教学示意；项目已有机制会在明确的小节中说明，不混作个人实施经历。

## 32.1 为什么最终答案和评分还不够

继续问同一道题：

> 小米 14 Pro 的屏幕尺寸和刷新率是多少？

参考事实是 6.73 英寸、动态 1～120Hz。假设某次回答把型号混淆了，而且用了很久才返回。

只看答案，你知道“错了”；只看总耗时，你知道“慢了”。但原因至少可能有四种：问题被改写错了；资料查错了；正确资料被后处理删掉了；材料正确但模型回答错了。慢也可能来自检索、模型等待、工具重试或多余的 Agent 轮次。

于是我们需要给这次回答保留一份有结构的过程记录。它不是为了收集越多数据越好，而是为了以后回答两个问题：**事实从哪一步开始偏离？时间花在了哪条路径上？**

## 32.2 先分清三个东西：整体成绩、过程地图、事件记录

| 名称 | 用最普通的话解释 | 在这道题里有什么用 |
|---|---|---|
| Metric，指标 | 把许多次执行汇成数字 | 最近一批参数题的正确性下降、首字等待变长 |
| Trace，调用链追踪 | 把一次执行拆成相互关联的步骤 | 这道题先改写、再检索、再生成，各走了多久 |
| Log，日志 | 记录某时某处发生的具体事件 | 改写后的查询是什么；工具为何重试；发生了哪种异常 |

三者可以这样配合：

```text
指标：参数题的延迟变差了
  ↓ 找到受影响的版本、时段和一条样本
Trace：这一题第二次知识工具调用占了很多时间
  ↓ 进入对应步骤
日志与输入输出：第一次已有完整答案材料，第二次参数却完全重复
  ↓
待验证的解释：Agent 没有正确使用工具结果，做了多余调用
```

日志也可以包含耗时，Trace 也可以挂事件和属性。区别不在于某个字段只准放在哪，而在于它们分别适合回答**总体怎么样、过程怎样走、局部发生什么**。这些术语的基础定义可对照 [OpenTelemetry 的信号说明](https://opentelemetry.io/docs/concepts/signals/)。

还有一个常被混淆的东西是聊天历史。聊天历史服务于“下一轮该让模型看到什么”；观测记录服务于“事后解释某次执行”。压缩了聊天历史，不意味着应覆盖旧执行记录；保存了聊天历史，也不意味着已经记录了检索耗时和重试。

## 32.3 Trace 是一条过程，Span 是其中一个有起止的步骤

把这次回答叫作 Trace T1。它内部的“问题改写”“知识检索”“调用模型”都可以各自成为一个 Span。

Span 至少应能说明：自己是谁、属于哪条 Trace、父步骤是谁、什么时候开始结束、结果怎样。它不是一行“开始检索”的日志，而是一个有持续时间的工作单元。

先看固定 RAG 的理想层次：

```text
Trace T1：处理一次手机参数问答
└─ answer.request
   ├─ query.prepare             整理历史、改写问题、确定检索范围
   ├─ knowledge.retrieve
   │  ├─ dense.search           稠密向量检索
   │  ├─ lexical.search         若本次实际启用了 BM25
   │  └─ graph.search           若本次实际启用了图谱检索
   ├─ evidence.prepare          融合、精排、去重、构建生成材料
   └─ answer.generate           模型请求至流结束
```

这张树表达的是包含关系，不表示三路检索一定串行。并行、先后和等待，要结合开始结束时间看。未启用的检索通道，不应伪造一个成功 Span；可以在配置快照中写清未启用。

再把知识检索放到 Agent 的工具中：

```text
Trace T2：Agent 完成一次手机参数问答
└─ agent.run
   ├─ model.call #1             输出知识工具调用及参数
   ├─ tool.call #1              执行知识工具
   │  └─ knowledge.pipeline    按工具实际实现展开内部步骤
   │     ├─ retrieve
   │     └─ prepare.result     可能还包含工具内模型调用
   ├─ model.call #2             读取工具结果，形成答案或继续调用
   └─ final.output
```

这时，RAG 是工具内部的能力，Agent Trace 还需要覆盖“选工具—执行—读结果—继续或结束”。只跟踪向量库 HTTP 请求，会漏掉“工具选错、参数错、重复调用”这些 Agent 层问题。

节点命名应稳定，如 `tool.call` 加工具名属性，不要把整句用户问题拼进节点名。目标是让同类步骤能比较，也让一条具体链路能展开。

## 32.4 为什么不能只存一个 session_id

同一个用户可以有多个会话；一个会话有多轮问答；同一道评测题又可以在不同版本、不同轮次中执行。只存“用户”和“问题”，以后很容易把不同答卷拼在一起。

在理想评测记录中，可以分开这些身份：

| 标识 | 标识什么 | 生命周期与用途 |
|---|---|---|
| `eval_batch_id` | 一批评测 | 将本批所有题与被评版本、数据集版本关联 |
| `query_id` | 题库里的题 | 同一道题跨版本比较时保持稳定 |
| `attempt_id` | 这道题的一次作答尝试 | 重跑另建一条，保留前次失败 |
| `session_id` | 一段业务会话 | 关联多轮输入，以及输入依赖的历史 |
| `trace_id` | 一次可追踪执行 | 从结果找到内部调用过程 |
| `span_id` / 父标识 | 其中一个步骤 | 还原嵌套、耗时和故障位置 |
| `tool_call_id` | 一次工具调用 | 配对模型提出的调用与工具返回结果 |

这些是讲解用的设计字段，不要求项目当前同名。工具内部一次网络重试仍属于同一个逻辑工具调用，但应有独立重试次数或子 Span；整道题重新作答则要有新的 `attempt_id`。

例如同一题第一次超时、第二次答错，不能只保留第二条，把它叫作“这道题的结果”。更不能拿第一次的检索记录和第二次的回答去算忠实性。

跨 Session 要不要关联？当问题依赖长期记忆或跨会话任务时，需要关联。但做法不是让同一用户几个月的操作共用一条 Trace。可以用受权限控制的任务标识、记忆条目及版本，把相关 Trace 连起来；每次执行仍有自己的起止。

例如上一会话写入了“用户常问小米 14”，下一会话明确问“14 Pro”。如果怀疑记忆污染，要能查到本次读了哪条记忆、哪个版本以及它来源于哪次写入，而不是盲目下载这个用户所有聊天记录。

## 32.5 跨线程、跨服务以后，怎样仍然是一条链

直觉上，Java 方法 A 调 B，很容易知道谁调用了谁。可是把检索放进线程池，或者由 Python 评测器调用 Java 服务，这个关系不会天然出现在数据库里。

理想做法是传递一个很小的**追踪上下文**：发送方带上当前 Trace 和父步骤身份，接收方据此建立自己的子步骤。跨 HTTP 可以用标准追踪头；线程池和异步回调则需要在调度时捕获、执行时恢复上下文，用完清理。OpenTelemetry 将这件事称为 [Context propagation](https://opentelemetry.io/docs/concepts/context-propagation/)。

这里的上下文是追踪身份，不是把用户历史、整个 Prompt 或密钥塞进请求头。第三方模型服务若不支持内部追踪，你仍然能记录自己这一侧“调用该服务”的耗时、状态以及它返回的请求编号，但看不到对方内部每层计算。

Python 和 Java 接入统一标准是一种扩展方案。不能直接把项目当前自定义的数字型 Trace ID 当作符合标准格式的追踪头使用；可新增标准 ID，并保留旧 ID 映射。

流式回答还有一个重要边界：**方法返回，不等于回答完成。** 发起 SSE 后，生成仍在继续。生成 Span 应在真正完成、失败或取消时结束，首个可见内容作为中间事件记录。否则系统明明让用户等了十秒，Trace 却只记到请求提交的几十毫秒。

## 32.6 RAG 最值得留下的，不是全部源码参数，而是证据的变迁

为了判断为什么把 14 Pro 答成了其他型号，可以保存五个关键检查点：

1. 实际用于检索的问题：有没有漏掉 `Pro`？
2. 各通道召回的候选：正确文档、相关块是否出现？
3. 后处理结果：正确块是否被精排、去重或截断丢掉？
4. 最终实际发送给回答模型的材料：两项目标事实是否都在？
5. 最终回答：哪些事实被使用、遗漏或改写错误？

每条证据至少应能回到文档/块身份和版本；需要分析内容时，再读取受控的文本快照。仅存块 ID 不够：几天后知识库更新，同一 ID 对应文本可能已经变化。仅存哈希也不够：哈希能比对内容是否一致，不能恢复内容。要解释旧答案，需要可解析的不可变快照引用，并保留顺序与截断信息。

这与本项目评测器的关系尤其重要：第 28 章说明，聊天请求和 `/rag/eval` 检索旁路是两次独立执行。后者不能自动充当前者真正使用过的材料。

理想改进是：聊天这次执行在构建模型输入的位置保存实际材料，评测答卷关联它；旁路重查则单独标识，用于对照。Agent 里还要区分“知识工具看过的原始材料”“工具返回给外层模型的结果”“外层模型实际输入”，不能把工具内部见过等同于最终模型见过。

## 32.7 模型和工具的轨迹应该记什么

对模型调用，重点是输入引用、模型与 Prompt 版本、采样配置、输出或工具调用、终止原因、耗时和可获得的 token 用量。对工具调用，重点是工具名称及版本、有效参数、结果引用、成功/失败、重试和外部操作结果。

“有效参数”值得强调：模型提议的参数可能经过校验、默认值补充和权限过滤。若只记录模型原始输出，就不知道工具最终到底查了哪个范围。

Agent 的过程透明，不等于必须获取模型隐藏的思维链。可观测、足以审计的行为是：模型收到什么允许记录的输入、输出了什么调用、工具实际执行了什么、返回了什么、最终做了什么。模型自己写的解释只是一个可核验的说法，不是对真实原因的保证。

HTTP 200 也只是通信层成功。工具可能返回“未找到资料”，Agent 可能毫无依据地作答，所以还要区分工具业务状态和任务完成状态。

## 32.8 评测器和裁判也需要身份，但不必挤进一条长 Trace

一次作答和几小时后的评分可以分开追踪：

```text
题目 S2-01 + 批次 B1 + 尝试 A1
  ├─ 作答 Trace T1 → 答卷 R1（回答、实际证据、版本）
  ├─ 独立旁路 Trace T2 → 对照检索记录
  └─ 评分 Trace T3 → 读取 R1 → 裁判版本 J1 → 分数与判定依据
```

重新评分可产生新的评分记录，仍指向同一份 R1；重新作答应产生新的尝试和答卷。用显式引用关联这些执行，比让一条 Trace 长时间不结束更清楚。

这样，评分为空时就能先问“答卷没生成、裁判失败，还是指标不适用”，而不是直接把空分当作答案零分。

## 32.9 回到原项目：基础已经有，扩展重点是什么

冻结源码中，`StreamChatTraceRunner` 建立一次 RAG 运行记录，关联 `conversationId`、`taskId`，并记录状态、时间和首内容事件。`RagTraceRunDO` 与 `RagTraceNodeDO` 分别承载运行和节点信息；节点有父节点、类型、耗时和错误信息。

源码入口：[Trace 入口](https://github.com/zz1403489227-crypto/AsterRAG/blob/98894c2c42c015a3c874c6b3c986ac863c85b731/rag/src/main/java/com/nageoffer/ai/ragent/rag/trace/StreamChatTraceRunner.java)、[运行记录](https://github.com/zz1403489227-crypto/AsterRAG/blob/98894c2c42c015a3c874c6b3c986ac863c85b731/rag/src/main/java/com/nageoffer/ai/ragent/rag/dao/entity/RagTraceRunDO.java)、[节点记录](https://github.com/zz1403489227-crypto/AsterRAG/blob/98894c2c42c015a3c874c6b3c986ac863c85b731/rag/src/main/java/com/nageoffer/ai/ragent/rag/dao/entity/RagTraceNodeDO.java)。流式细节可回查[第 13 章](13-answer-generation-and-trace.md)。

因此，理想设计不是“先安装一个工具才算有 Trace”。首先应把现有记录与评测答卷、实际模型上下文以及 Agent 工具调用关联好。以后若要统一跨进程采集，再考虑标准化追踪。

面试官问“用什么工具记录”，可以这样答：

> 我研究的项目已经有自定义的 RAG 运行和节点记录。如果扩展评测可观测性，我会先补齐答卷与实际执行轨迹的关联；跨 Python 和 Java 时，可以用 OpenTelemetry 统一采集和传播追踪身份，再接存储与查询界面。采集标准、存储系统和展示界面是三件事，关键仍是把 Agent/RAG 的业务步骤记录完整。

## 32.10 本章要能讲出的完整回答

> 我会把整体指标、单次调用链和局部日志分开。指标发现哪类问题变差，Trace 展示这一次请求经过的模型、工具和检索步骤，结构化日志与输入输出快照解释具体发生了什么。评测中用批次、题目和作答尝试关联答卷，记录实际生成材料，而不是用另一次检索替代。会话负责关联多轮，每次执行单独追踪；Agent 重点记录可观察的工具决策与结果，不依赖隐藏思维链。
