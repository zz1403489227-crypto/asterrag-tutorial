# 第 25 章：Agent 怎样使用 RAG——从一次检索到能够继续行动的问答系统

> 前四章讲清了知识能力怎样建立、怎样检索。本章把视角拉回整个项目：谁决定使用知识能力，拿到结果以后怎样继续，为什么这与固定 RAG 流程不同。

## 25.1 先看固定 RAG 已经解决了什么

用户提出问题，系统改写问题、检索资料、筛选证据、调用模型生成回答。虽然其中可能有模型、分支和并行检索，但整体步骤由程序事先安排。

```text
问题 → 理解与改写 → 检索 → 整理证据 → 生成回答
```

对于“星河项目的外包工程师林辰出差，费用由谁审批”，这条流程已经很有用。它可以取得身份、制度和负责人材料，再形成答案。

但实际请求还可能更开放：第一次信息不够，需要补查；用户想比较两项制度；任务既要读知识库，又要查询外部业务状态。每一种情况都预先写成固定分支，流程会越来越复杂。

Agent 多提供了一层能力：**让模型根据当前目标和已有结果，决定下一步采取什么行动，而不是每次只走完预先固定的一条查询链。**

## 25.2 Agent 并不是模型单独在运行

把模型想成决策者还不够。它需要一个执行循环，把决定变成真正的工具调用，再把结果交回来。

一个最小的 Agent 循环可以这样理解：

```text
用户目标 + 当前上下文
          ↓
       调用模型
          ↓
   ┌──────┴────────┐
   │               │
给出回答         请求调用工具
   │               ↓
本轮结束        程序执行工具
                   ↓
             取得工具结果
                   ↓
             更新模型上下文
                   └────────→ 再次调用模型
```

模型负责选择行动及参数，程序负责执行，工具返回观察结果。模型再根据新增信息决定继续还是结束。

ReAct 通常用“推理—行动—观察”概括这一循环。对工程理解而言，最关键的是信息怎样更新：**工具结果成为下一轮模型决策的输入。** 不需要把它理解成必须向用户展示一大段内部思考文字。

本项目使用 AgentScope 提供这类循环的执行能力，自己的代码负责接上工具、会话、记忆和输出。

## 25.3 RAG 怎样成为 Agent 的一个工具

工具可以先理解成模型能够请求程序完成的一项能力。模型看到工具名称、用途和参数要求；程序看到具体调用后，执行对应实现。

本项目提供知识工具 `search_knowledge(query)`。模型只需提交一个独立完整的问题，工具内部负责执行前几章讲的知识处理：

```text
Agent 提交 query
      ↓
知识工具
  改写 / 拆分 → 知识意图与范围 → 多路召回
      → 融合 / 精排 / 证据处理 → 知识答案合成
      ↓
工具结果回到 Agent
```

这是一种很重要的组合方式：外层负责决定“什么时候用知识能力、要问什么”，内层负责把“查知识”这件事做好。

就像一个负责人可以安排检索员查资料，不需要在每次安排时重新决定检索员怎样分词、怎样建立倒排索引、怎样调 HNSW。

所以，项目里的动态性主要在外层行动选择。HNSW、BM25、LightRAG 位于工具内部的检索层，它们没有在当前知识工具参数中作为三个独立按钮交给模型选择。

## 25.4 跟随林辰的问题，走一轮完整的信息流

现在把所有章节连接起来。

**第一步，外层接收用户问题。** 模型看到用户询问项目内部审批规则，判断需要知识库，而不是只凭常识回答。

**第二步，模型生成工具请求。** 请求包含工具名 `search_knowledge` 和 query：“星河项目的外包工程师林辰出差，费用应该找谁审批？”

**第三步，程序执行知识工具。** 内部理解问题，搜索相关库。向量、词面和图谱能力在启用时提供候选，随后经过融合、精排与证据整理。

**第四步，知识工具形成结果。** 本项目的知识工具不只返回原始片段，它还调用模型，基于本轮证据合成一段知识答案。例如：“林辰属于星河项目外包人员；按外包差旅规定，应由星河项目负责人周宁审批。”

**第五步，结果进入外层上下文。** Agent 模型再次被调用，此时它不再只拥有用户问题，还拥有知识工具的答案。

**第六步，外层决定下一步。** 如果结果已满足目标，就形成面向用户的回复；如果结果指出条件不明确，可能需要询问用户；如果还有未解决事项，可以继续调用工具。

这里描述的是一种合理行动轨迹，而不是要求模型每次固定执行相同步数。正是因为后续决定取决于观察结果，它才不同于“一次查完就结束”的固定链。

## 25.5 为什么工具里已经用了模型，外面还可以有模型

初看会觉得重复：知识工具内部已经合成答案，Agent 为什么还要再看一遍？

因为两层处理的目标不同。工具内的模型围绕本次知识问题组织证据；外层模型负责用户的整体任务，可能还要整合其他工具结果、决定补问或继续行动。

可以把两者理解为“专题答复”和“整体任务处理”。用户只问一个简单知识问题时，两层可能显得更重；任务包含多个步骤或多种能力时，这种组合更灵活。

它也有一个明确取舍：工具先合成，返回更紧凑、容易阅读的结果；代价是增加处理步骤，并把原始证据压缩成了一次中间表达。若任务强调细粒度引用，工具结果还可以设计得更结构化，这是后续工具设计可以讨论的方向。

对当前项目，记住实际数据流即可：**原文证据在知识工具内部处理，外层收到的是工具结果文本，而不是自动拿到所有片段分数与来源对象。**

## 25.6 动态补查为什么有用

假设用户最初只问：“林辰这次出差找谁审批？”第一次知识查询若只明确了“外包人员由项目负责人审批”，却没有确定项目或负责人，外层就面临一个新的信息缺口。

它可以围绕缺口继续询问或检索，而不是对空白部分随意补一个名字。新的问题可能是“林辰目前参与哪个项目”，也可能是“星河项目负责人是谁”。拿到新结果后，再补齐答案。

这揭示了 Agent 的实际价值：把“解决问题”拆成可以根据中间结果继续调整的过程。每一步的工具调用都应该为目标补充信息，或者完成所需行动。

同时，循环需要结束条件。已经获得足够信息时应回答，关键条件缺失时应澄清，反复无进展时应停止无效重复。AgentScope 的循环限制和项目的任务生命周期为这个过程提供运行约束；具体实现可继续读原教程第 14～16 章。

## 25.7 知识、业务工具和记忆各解决什么

这三种能力都可能被 Agent 使用，但不要因为都叫工具就混成一类。

| 能力 | 回答的问题 | 典型输出 |
|---|---|---|
| 知识工具 | 文档中的制度、说明、事实怎么说？ | 检索并整理的知识结果 |
| MCP 业务工具 | 外部系统中的某项功能或数据是什么？ | 业务接口返回的结果 |
| 记忆能力 | 之前的对话或长期信息有哪些仍然相关？ | 有助于当前决策的历史信息 |

查询差旅制度是在读知识；查询一个业务系统的当前状态，是调用对应业务能力；理解“还是我上次那个项目”，可能需要会话记忆。

Agent 的灵活性来自把这些能力放到同一决策循环里。知识检索并没有被替代，它成了其中一项可以反复调用的重要能力。

## 25.8 再从全局看项目：三层各自解决一个问题

现在可以画出一张足够用于面试开场的架构图：

```text
第一层：Agent 任务处理
  理解目标 → 选择工具 → 观察结果 → 继续或回答
                         │
                         ↓
第二层：RAG 知识能力
  问题理解 → 检索 → 融合精排 → 整理证据 → 合成结果
                         │
                         ↓
第三层：知识组织与查找
  稠密向量 + HNSW │ 文本倒排 + BM25 │ 实体关系 + LightRAG
```

第一层决定下一步做什么，第二层把查知识组织成可靠的处理步骤，第三层提供不同的资料组织和搜索方法。

如果模型没有调用知识工具，优先分析第一层；如果查到了不适用的规定，分析第二、三层；如果向量近邻查询慢，才进一步看索引与查询参数。

这种层次感能让你面对追问时迅速定位，而不是从任何问题都开始背 Redis、RocketMQ 或 Spring Boot。

## 25.9 面试时如何把重点讲出来

开场可以这样组织：

> 这个项目的核心是把 Agent 和 RAG 分层组合。外层通过 AgentScope ReAct 调用知识、记忆和业务工具；知识工具内部包含问题理解、多路召回、融合精排和答案合成。我重点研究三种检索方式为什么互补：HNSW 解决向量近邻查找效率，BM25 补充词面线索，LightRAG 用实体关系连接跨文档知识。它们最后服务的是同一个目标：给 Agent 的行动与回答提供合适的依据。

随后让面试官沿着主线追问：

- 问索引：讲图如何建立、查询如何分层导航，接第 21 章。
- 问混合检索：讲语义、词面、关系三个观察角度，接第 22～24 章。
- 问 Agent：讲工具结果如何进入下一次决策，接本章与第 14～16 章。
- 问回答质量：讲资料是否齐全、排序是否保留关键条件、模型如何使用证据。

如果面试官问个人工作，再清楚说明基于开源项目完成了哪些研究、教程或真实改动。介绍系统原理与说明个人贡献是两个话题，不需要在每段原理解释里反复插入归属声明；也不能把上游已有功能变成个人开发成果。

## 25.10 后端应该怎样放在合适的位置

后端组件承载任务，不必成为项目介绍的主角。它们在回答某个具体问题时再出现：

- 用户发起长任务，怎样管理状态和取消？需要任务生命周期与协调机制。
- 文档处理耗时，怎样异步完成？需要入库任务与消息机制。
- 会话跨请求延续，哪些状态应保存？需要持久化和记忆管理。

这样讲，组件是为了支撑前面的能力而存在，而不是为了凑一份技术栈清单。你既保留了系统完整性，又把面试的中心放在 Agent 与 RAG。

## 25.11 五章最终汇成一条主线

> 文档先被组织成可检索知识：向量索引便于按语义查找，倒排索引便于按词语定位，知识图谱便于连接实体关系。问题到来后，检索管线收集、融合并挑选证据；外层 Agent 决定何时调用这项能力，并根据结果继续行动或回答。

能把这句话展开成建库、查询、Agent 循环三条具体流程，就抓住了项目的核心。类名和配置是之后定位实现的地图，不应该取代这个理解。
