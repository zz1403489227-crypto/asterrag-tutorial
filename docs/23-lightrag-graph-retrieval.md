# 第 23 章：LightRAG——把散落的文字连成知识，再沿关系找答案

> 本章的主线是：文档怎样变成图，问题怎样进入图，图中的关系怎样带回原文，最后怎样形成答案。先理解这一整套方法，再看项目如何接入它。

## 23.1 先看一个只靠单段文字不容易回答的问题

仍然是这四份资料：

```text
D1 人员记录：林辰是远山科技的外包工程师，目前参与星河项目。
D2 项目介绍：星河项目的负责人是周宁，远山科技为项目提供研发支持。
D3 外包规定：外包人员因项目出差，费用由所在项目的负责人审批。
D4 员工规定：正式员工的差旅费用由直属经理审批。
```

用户问：“星河项目的外包工程师林辰出差，费用应该找谁审批？”

人阅读这些资料时，并不是只找一句最像问题的话。我们会做三件事：确认林辰是什么身份；找到这个身份适用的规则；把规则里的“项目负责人”落到星河项目的具体人员周宁。

```text
林辰是外包人员
      ＋
外包项目差旅由项目负责人审批
      ＋
星河项目负责人是周宁
      ↓
这次费用应找周宁审批
```

答案来自几条知识之间的连接。单看 D1，没有审批规则；单看 D3，没有负责人姓名；单看 D2，也不知道哪类费用适用。

普通向量检索当然可能把这几段都找回来，但它主要把文档看作一组可比较的文本块。图谱方法多做了一步：**在用户提问之前，就把文本里反复出现的实体和关系抽出来并连接起来，让查询能够利用这种结构。**

## 23.2 什么是知识图谱：把一句话拆成可连接的事实

先从最简单的形式开始：

```text
主体 ——关系——> 客体
```

“星河项目的负责人是周宁”可以表示为“周宁——负责——>星河项目”。“林辰来自远山科技”可以表示为“林辰——所属单位——>远山科技”。

把资料中的关系画出来，可以得到这样的语义地图：

```text
林辰 ──所属单位──> 远山科技 ──提供研发支持──> 星河项目
  └────────────────参与──────────────────> 星河项目
                                            ↑
                                            │ 负责
                                           周宁

外包人员项目差旅 ──审批角色──> 所在项目负责人
正式员工差旅     ──审批角色──> 直属经理
```

箭头表示我们阅读时理解的关系方向。图数据库里具体如何编码，是实现层的另一件事。

这张图比简单的关键词表多了什么？关键词表知道“周宁”和“星河项目”在同一篇材料里出现；图谱还保留了它们之间的含义——周宁负责这个项目。仅有“共同出现”与明确的“负责关系”，能够支持的检索和解释是不一样的。

节点也不局限于人和公司。项目、制度、产品、疾病、技术概念都可以成为实体。重要的不是节点名称听起来像不像一个东西，而是它是否值得作为跨文本连接的中心。

## 23.3 图是怎么从文档里长出来的

LightRAG 的索引过程可以分成三类工作：从文本抽取实体和关系；为这些实体关系形成可检索的描述；合并不同片段中的重复知识。这样建立的图与文本表示结合起来，供后续检索使用。[LightRAG 原论文](https://arxiv.org/html/2410.05779v1)

我们用自己的四份资料走一遍。

### 第一步：让模型读片段，找出实体与关系

读 D1，模型可以识别林辰、远山科技、星河项目，以及“所属单位”“参与”等关系。读 D2，又识别周宁、星河项目、远山科技，以及“负责”“提供研发支持”等关系。

这里调用模型的目的不是回答用户问题，而是对资料进行结构化加工。它发生在知识构建阶段，输出面向后续索引。

为什么不用一个简单的词典就做完？因为关系经常藏在不同表达里：“由周宁牵头”“负责人：周宁”“周宁承担项目管理职责”，在语义上可能指向相近关系。模型能够从自然语言中识别这种含义，而不是只认某个固定句式。

### 第二步：不要只保留两个名字和一条线

假设我们只存“周宁—星河项目”这一条边，却把“负责什么、在什么情境下负责、依据哪段资料”都丢掉，图虽然连起来了，但可解释的信息仍然很少。

因此，节点和关系还需要描述。以我们的例子，可以把实体“周宁”理解为一张知识卡：它说明这个人在材料中的身份、相关项目，以及信息来源。关系也有自己的说明，例如“周宁负责星河项目的项目管理”。

这些描述有两个用途：一是让后续语义检索能找到这条知识，二是为答案生成提供可阅读的上下文。图并不是一堆没有文字的圆点和线。

### 第三步：把不同片段里的同一实体接到一起

D1 和 D2 都出现“星河项目”。如果每读一段就新建一个互不相连的“星河项目”，跨文档联系仍然没有建立。

所以要把指向同一实体的记录合并，汇集它的关系和描述。合并后，“林辰参与的项目”和“周宁负责的项目”变成同一个节点，前后两份材料就通过它连通了。

```text
读 D1：林辰 ──参与──> 星河项目（第一次出现）
读 D2：周宁 ──负责──> 星河项目（再次出现）
                           ↓ 合并
             林辰 ──参与──> 星河项目 <──负责── 周宁
```

这就是为什么图谱能够连接跨片段信息。不是查询时碰巧把两句话放在一起，而是索引阶段已经建立了可复用的连接。

### 第四步：保留回到原文的路

实体和关系是从文本抽取的摘要，不应该成为脱离原文的孤岛。

当一条关系记录“周宁负责星河项目”时，还要能找到支撑它的 D2；当一条规则说明外包差旅审批角色时，要能取回 D3 的原文。图谱负责组织线索，原文保留完整条件和细节。

因此，建图不是把原文压缩完就扔掉，而是增加一层导航结构：从问题到实体关系，再从实体关系回到相关文本。

## 23.4 一个容易忽略的关键：有了图，为什么还需要向量索引

图擅长回答“这个实体和谁连接”，但用户不会总是输入精确的实体名或关系标签。

用户可能问“谁给林辰的差旅签字”，图里的描述却写“费用审批职责”。如果只按字符串完全匹配关系名称，仍然会漏掉这个入口。

LightRAG 因此把图和向量结合起来：为实体、关系构造文本表示并建立向量检索入口。问题中的具体线索可以检索实体表示，主题性线索可以检索关系表示，再利用图补齐相邻信息。[LightRAG 官方检索实现](https://github.com/HKUDS/LightRAG/blob/main/lightrag/operate.py)

把分工画出来就很清楚：

```text
向量索引：这个问题应该从哪些实体 / 关系进入图？
                         ↓
知识图谱：这些实体 / 关系与哪些信息相连？
                         ↓
原文存储：支撑这些信息的具体材料是什么？
```

传统向量 RAG 常把“文本片段”作为主要检索对象。这里不仅可以找片段，还可以先找到“周宁”“星河项目”或“差旅审批职责”这样的知识入口。

这也是两种“图”的根本区别：HNSW 的边帮助搜索向量位置；知识图谱的边表达业务含义。LightRAG 用到向量检索时，底层还可能使用近邻索引。两种结构可以同时存在，各管一层。

## 23.5 问题怎样变成两个检索入口

现在开始查询。对于“星河项目的外包工程师林辰出差，费用应该找谁审批”，先把线索分成两类：

| 线索层次 | 例子 | 想解决的问题 |
|---|---|---|
| 具体实体 / 细节 | 林辰、星河项目 | 问的是谁、哪个对象？ |
| 主题 / 关系 | 外包差旅、费用审批、审批职责 | 想知道哪一类关系或规则？ |

LightRAG 将两类线索称为 low-level 和 high-level 关键词。不要把这里的“关键词”直接理解成上一章的 BM25 分词：这里是让模型概括查询的具体对象与抽象主题，后面可以用这些线索做语义检索。[LightRAG 查询关键词设计](https://github.com/HKUDS/LightRAG/blob/main/lightrag/prompt.py)

为什么需要两个入口？如果只抓住林辰，可能取得一堆人员履历却没找到审批规则；如果只抓住费用审批，可能找到通用制度却不知道星河项目负责人是谁。问题既有“哪个人”的约束，又有“什么关系”的需求，两路需要互相补充。

## 23.6 local：从具体实体出发，找它周围的知识

local 的直觉是：“先找到问题说的那个对象，再看它连接了什么。”

沿我们的例子，可以这样理解这条查询路：

1. 用“林辰、星河项目”等具体线索，搜索相关实体表示。
2. 取得命中的实体信息，例如林辰的外包身份、星河项目的描述。
3. 收集这些实体周围的相关关系，例如参与、负责和研发支持。
4. 沿来源关联，取得支撑这些实体关系的文本片段。

这样，用户即使没有在问题中写出“周宁”，检索仍有机会通过“星河项目—负责人”的关系取到这个名字。

图检索不要求把整张图从头走一遍。先用向量检索定位少量入口，再围绕入口获取相关结构，是把搜索范围控制住的关键。

这一类方法特别适合“某人负责什么”“某产品依赖什么”“某项目关联哪些组织”等有明确对象的问题。

## 23.7 global：从关系主题出发，找相关的一组知识

global 换一个方向：“先找与问题主题有关的关系，再看这些关系连接哪些对象。”

对于本例，“外包差旅审批职责”可以帮助定位 D3 表达的审批规则。取得相关关系后，再补齐关系两端涉及的实体、描述和来源。

它与 local 的区别不在于一个只能搜小库、另一个扫描全库，也不是一个走一跳、另一个固定走很多跳，而在于主要检索入口不同：

```text
local：具体实体线索 → 实体 → 相关关系 → 支撑文本

global：主题关系线索 → 关系 → 相关实体 → 支撑文本
```

global 更适合“几类因素如何影响某个结果”“这批制度如何分配职责”等主题性问题。这里的“全局”首先强调关系和主题层次，不应理解为必须把整张图都展开后塞给模型。

## 23.8 hybrid：把“问的是谁”和“问的是什么关系”拼起来

LightRAG 的 hybrid 结合 local 和 global 两种检索思路。对本例，local 带回人员和项目关系，global 带回外包差旅审批规则。

但两路结果还需要整理：重复的实体关系要合并，相关文本要选取，过多内容要按预算收窄。最终不是把图数据库的原始节点对象直接交给模型，而是组织成模型能读的上下文。

```text
                       用户问题
                          ↓
                    提取两类线索
                   ↙            ↘
       林辰、星河项目            外包差旅、审批职责
               ↓                        ↓
       检索实体，补关系          检索关系，补实体
                   ↘            ↙
                 合并相关知识与来源
                          ↓
               取回、整理支撑文本片段
                          ↓
                     回答上下文
```

这里的 hybrid 是 LightRAG 内部两种图谱相关检索思路的组合。下一章还有项目外层的“向量 + BM25 + 图谱”融合，那是另一个层级。先在一个通道内部组合方法，再把整个通道作为更大系统的一路，是很常见的系统设计。

## 23.9 图找到了材料，最后的答案是谁形成的

假设整理后的上下文包含三条关键信息：

- 林辰是星河项目的外包工程师。
- 外包人员的项目差旅费用由项目负责人审批。
- 星河项目的负责人是周宁。

模型现在能够把角色和具体人员联系起来，形成“应由周宁审批”的答案，并说明依据。

请注意这里真正发生的合作：图与索引负责找到连接问题所需的材料；模型负责阅读这些材料，将规则适用到具体对象，并用自然语言解释。图数据库没有自己执行一段“遇到差旅就输出周宁”的业务代码。

如果原文还写着“超过某金额需财务复核”，取回原文就很重要。单独一个“审批角色”关系可能容纳不下所有附加条件；完整答案需要利用关系描述与原始文本共同表达。

这也是图谱检索中最值得记住的一句话：**先利用结构找全相关知识，再利用文本解释具体条件。**

## 23.10 整套方案真正换来了什么，又付出了什么

它把一部分理解工作提前到了建库阶段。以后不同用户反复询问星河项目时，可以复用已经抽取的实体和关系，而不是每次都从互不相连的文本块开始。

它也让“通过关系发现未在问题中出现的信息”变得自然。用户只提到项目，系统仍可能找到负责人、供应商或适用制度。

代价同样清楚：建库要做实体关系抽取和描述整理，比单纯生成片段向量更复杂；名称歧义会影响合并；抽取遗漏可能让关系不完整；原文更新后，派生的图和描述也要跟着更新。

因此，图谱最有吸引力的场景是实体多、联系强、问题经常需要跨资料连接知识。若材料本身很短，答案总在一个清楚的段落里，直接向量或关键词检索可能已经足够。是否值得引入图谱，取决于它能否解决实际的知识连接问题。

## 23.11 回到本项目：LightRAG 被放在哪个位置

前面解释的是 LightRAG 的方法原理。本项目把它接为一个可选图谱通道：

```text
知识入库时：文档文本与来源 → LightRAG → 构建其知识索引

问答检索时：问题 → LightRAG → 上下文与来源
                                   ↓
                            项目的统一候选池
                                   ↓
                          融合、精排、答案生成
```

配套服务使用 Neo4j 保存图结构，LightRAG 还使用自己的文本、向量和状态存储。Neo4j 管节点和关系，LightRAG 编排抽取与检索，模型处理文本理解，这三者的工作不要混在一起。

Java 客户端请求 LightRAG 时设置 `only_need_context=true`：这里先取证据，让图谱路与向量、BM25 一起参与项目自己的后续处理，而不把 LightRAG 直接当作最终回答出口。其配置采用 hybrid 查询模式，图谱能力默认关闭。

项目级源码落点集中在文档同步、LightRAG 请求和结果转换。接口字段、库范围处理和更新细节已放在附录，理解原理后再查即可。

## 23.12 用两条流程检查自己是否真正理解

建库流程应当能说成：

> 文档分段后抽取实体和关系，为它们形成描述，合并跨段重复知识，保留原文来源，再为实体与关系建立可检索的表示。

查询流程应当能说成：

> 把问题拆成具体对象与主题关系两类线索，找到相关实体和关系，补齐相邻知识，取回支撑文本，整理上下文，再形成回答。

能把这两条链说顺，就已经抓住图谱 RAG 的主体。下一章把它与 HNSW 向量路、BM25 词面路放到同一张检索流程里。
