# 第 46 章 为什么让本地 Qwen 分担部分模型调用

用户问：“这款手机能不能一边导航一边拍视频？和另一款相比哪个更适合旅行？”系统需要理解指代、拆分问题、找资料，再组织答案。如果走 Agent，还要先决定搜什么，必要时继续搜索。

这些步骤都可能用到模型，但难度和出错代价不同。把它们全部交给同一个昂贵模型，容易让简单处理消耗过多预算；全部交给小模型，又可能损失检索准确性和最终回答质量。本章设计一种分工：**让本地 Qwen 承担边界明确的语义处理，云端模型承担最终回答和 Agent 决策。**

读完应能回答三个问题：为什么选这些环节；固定 RAG 与 Agent 的费用为什么不能用同一个百分比；怎样证明省下了钱且没有明显损害效果。

产品事实沿用冻结源码 `98894c2c42c015a3c874c6b3c986ac863c85b731`。本章的任务级分流是拟议改造，不是已经部署的功能；百分比是带工作量假设的估算，不是实验成绩。源码锚点集中在章末，正文先讲机制。

## 46.1 先看分工后的完整请求

下面这张图表示建议方案，方便先建立地图。真实代码里，有些节点需要按条件触发，箭头不代表每次都会执行。

```text
                       用户问题
                          │
            ┌─────────────┴─────────────┐
            │                           │
         固定 RAG                  云端 Agent 决策
            │                           │
            │                      search_knowledge
            │                           │
            └───────┬───────────────────┘
                    ↓
       本地 Qwen：改写、拆分、意图识别
                    ↓
       检索：向量 / BM25 / LightRAG
       LightRAG 关键词提取可转本地 Qwen
                    ↓
          候选融合、重排、证据整理
                    ↓
             云端模型合成答案
                    │
           ┌────────┴───────────┐
           ↓                    ↓
      固定 RAG 返回       作为工具结果交回 Agent
                                ↓
                      继续调用工具或最终回答

旁路辅助：标题、推荐问题、条件触发的摘要 → 可交本地 Qwen
独立评测：RAGAS 裁判 → 第一阶段保留原有云端裁判
```

图中最重要的是最后一段：本项目的 `search_knowledge` 不是把原始检索块直接交给 Agent。`KnowledgeSearchFacade.search()` 内部还会调用一次 LLM，根据证据合成答案，然后才返回给 Agent。因此，一次 Agent 知识搜索包含“内部知识处理”和“外部 Agent 决策”两个模型层次。

第一阶段保留这两个层次中的云端答案生成，先迁移前面的改写、意图和图谱关键词处理。这使改动集中在可独立观察的节点，也给以后迁移工具内答案生成留下对照基线。

## 46.2 简历上的调用数量应该怎样理解

当前 Java 产品代码中，能够定位到 **16 处文本 LLM 业务调用入口**：15 处 `LLMService` 调用表达式，加上 1 处进入 Agent 运行循环的入口。再加 2 处视觉模型调用、3 处 Embedding 调用、1 处 Rerank 调用，共 22 处模型调用位置。

这个数字反映梳理范围，不是每次问题的调用次数，也不包含外部 LightRAG 和评测器内部的全部调用。固定 RAG 的正常回答与兜底有两个代码位置，但通常只走一个；PG 与 Milvus 的查询向量化也是替代实现。Agent 的循环入口只有一个，却可能产生多轮模型请求。

面试时可以说“梳理了 16 处文本模型调用入口”，不要说“每道题固定调用 16 次 LLM”。后一句会让所有成本推导都失去依据。

| 业务阶段 | 文本调用位置数 | 触发规律 |
|---|---:|---|
| 改写拆分、意图识别、歧义判断、Workflow MCP 参数提取 | 4 | 有条件分支；拆分后可能多次意图识别 |
| 固定 RAG 正常回答与兜底 | 2 | 两个生成分支 |
| Agent 知识工具内部合成 | 1 | 每次有效知识搜索可能发生 |
| 推荐问题与标题 | 2 | 推荐是独立入口，标题主要在新会话生成 |
| 固定 RAG 历史摘要 | 1 | 长历史达到条件才发生 |
| Agent 主循环 | 1 | 一个入口，多轮模型调用 |
| Agent 对话摘要、长期记忆抽取、记忆合并 | 3 | 随历史、待处理材料和容量条件触发 |
| 可选入库增强与元数据提取 | 2 | 取决于是否使用对应入库节点 |
| 合计 | 16 | 不等于单次请求的调用量 |

“图谱服务开启”也不意味着每道题都重建图谱。入库时的实体关系抽取是一类成本，查询时的关键词提取是另一类。要分别记账。

## 46.3 为什么这些任务适合分给本地 Qwen

### 问题改写：目标明确，输出容易比较

用户上一轮问过某款手机，这一轮问“它支持多少倍变焦”。改写的目标是补回明确的型号，而不是回答变焦倍数。模型只要保留实体、约束、否定词和问题意图，把依赖上下文的表达变成可检索问题即可。

这类任务通常不需要广泛的世界知识。系统已经提供近期对话，模型的工作是整理输入。选择本地 Qwen 的理由是：可以用相对小的模型处理频繁、短输出的任务，并针对实体保留、约束保留、拆分完整性分别检查。

但“容易检查”不等于只检查 JSON。把“不超过 3000 元”改成“3000 元以上”，输出格式完全合法，检索方向却已经错了。因此应保留原问题与改写结果，对关键实体、数字和否定条件进行核对。改写失败时是否退回原问题，是需要明确设计的降级语义。

### 意图识别：在已知候选范围里选择

本项目会把意图树等信息交给模型，让模型判断问题涉及哪些目标。这里的任务接近受约束分类：在系统给定的标签集合中选择，而不是自由发挥一个新类别。

小模型值得承担这项工作，因为选择范围明确，输出可以做标签合法性与结构校验。困难集中在相近意图、多标签问题和知识库作用域，而不是文章生成能力。

意图识别的错误影响很大：模型把产品参数问题路由到售后政策，后面的强模型也可能拿不到正确材料。因此它适合成为“优先验证的本地任务”，不能因为输出短就默认准确。需要比较意图准确率、多意图召回，以及最终检索 Recall 是否下降。

当前源码的意图识别走 STANDARD 档。它与最终回答共用档位，是本方案需要做任务级路由的直接原因。

### 图谱关键词提取：提炼检索入口

LightRAG 查询需要从问题中提取用于实体和关系检索的关键词。例如“某款手机适不适合户外拍摄”，具体型号是实体线索，防抖、防水、续航等可能构成关系和主题线索。

这一步不是让模型凭记忆回答，而是从问题里组织搜索线索。因此可以考虑用本地 Qwen。模型需要保留专业名词，避免把相近产品混为一谈；评价它应看找回了哪些证据，而不只看关键词是否写得漂亮。

项目向 LightRAG 发送 `only_need_context=true`，只取检索上下文，因此这里没有额外一层 LightRAG 最终回答生成可供“省掉”。关键词抽取是否命中缓存、是否允许直接传关键词，以及具体调用次数，要以实际部署版本为准。

### 摘要：材料已经给定，但遗漏有累积效应

长对话摘要把大量历史整理为较短的状态说明，例如用户的预算、已排除的型号、尚未解决的问题。它同样主要依赖给定材料，不需要模型独立搜索知识。

本地化的价值在多轮会话中体现：摘要可以异步或在预算允许时执行，重复处理的成本较容易控制。但摘要中的错误会传给后续多轮。把“用户不接受曲面屏”漏掉，会导致系统反复推荐不合适的机型。

因此应优先保留实体、数字、否定条件、未解决事项和来源轮次，不应只追求压缩比。长期记忆的抽取与合并还会改变持久状态，影响比临时摘要更长，应在对话摘要之后逐步迁移，不能把三者当成同等低风险任务。

### 标题和推荐问题：低风险，但直接省钱很少

标题生成失败通常不影响核心回答，所以它适合验证本地接口、并发和超时。不过当前轻任务首选 Qwen-Flash，API 单价已经很低。只把标题和改写转本地，不太可能让整条链路费用骤降。

这说明两个优先级应分开：**最适合先接入的任务，不一定是最值得为省钱投入的任务。** 低风险任务用于建立稳定接口；较昂贵且高频的意图、抽取和摘要任务，才可能带来更明显的节省。

## 46.4 为什么第一阶段不把所有生成都迁走

云端最终回答需要融合可能冲突的材料、回答复合问题、处理证据不足和生成引用。Agent 决策又需要判断何时搜索、怎样构造工具参数、失败后怎么办以及何时停止。它们都比标题生成更难用简单规则完整检查。

当一个便宜模型多搜索两轮才完成任务时，它可能消耗更多总 Token，并把工具和后续云端模型的费用一起抬高。如果错误结束任务，费用看似降低，实际上只是交付质量下降。

因此第一阶段保留云端 Agent 主模型和最终答案生成，把模型能力集中在困难决策上。这个选择不是认定 Qwen 不能做 Agent，而是让第一次改造只有一组主要变量：同样的主模型、同样的工具和检索策略，仅替换辅助处理模型。

对于知识工具内部的答案合成，也可以做第二阶段实验。它已经拿到明确证据，本地化可能再省一部分费用；但要观察信息遗漏、引用线索丢失，以及 Agent 是否因工具答案不完整而重复搜索。本章简历估算没有把这一步提前算成已经本地化。

## 46.5 为什么选 Qwen，而不是笼统地说本地小模型

首先，产品已有 `qwen3-local` 和 Ollama 的兼容接口适配，不必重新设计整个调用边界。其次，这个项目以中文知识问答、分类和抽取为主，Qwen 是值得验证的候选，能够沿用统一的请求、结构化输出和模型服务方式。

这两个理由只能支持“接入成本较低、任务方向匹配”，不能证明 Qwen 在我们的评估集上胜过其他模型。8B、14B 或更大模型的选择，最终要看结构化输出成功率、任务效果、延迟和显存，而不是只看参数量。

以本项目已配置的 Qwen3 系列为起点，可以先考虑 8B 或量化的 14B。FP16 权重的粗略体积是参数量乘 2 字节：8B 约 16GB，14B 约 28GB；推理还需要 KV Cache、运行时和临时内存。因此不能把“权重能放下”当成“长上下文和并发都能放下”。量化可降低权重占用，但也有精度、兼容性与速度取舍。

服务器只读检查确认存在 24GB 级 GPU，不过有其他任务运行。资源使用必须单独安排。这里不预设独占卡、不抢占已有进程，也不把一次显存快照写成长期容量保证。

服务层可使用 Ollama，也可使用 vLLM 的兼容接口。具体需要检查的不是“接口名字一样”，而是模型名、聊天模板、JSON 输出、思考模式、流式事件和工具调用协议是否匹配。参考 [Qwen 的 vLLM 部署文档](https://qwen.readthedocs.io/en/latest/deployment/vllm.html)。

## 46.6 在项目中怎样落地分流

### 普通 LLM 路由与 Agent 模型是两个入口

普通业务通过 `LLMService` 进入模型选择和供应商适配。当前 FAST 候选顺序是 Qwen-Flash、Qwen-Plus、本地 Qwen；STANDARD 首选 Qwen3-Max，本地 Qwen同样不是第一候选。

将本地模型移到 FAST 第一位，能够改变部分轻任务，却不会迁移使用 STANDARD 的意图识别。反过来，把 STANDARD 全部换成本地，又会连最终回答一起改掉。

建议增加用途级选择，例如“改写、意图、歧义、摘要、回答”各有自己的模型与超时策略。实现时可以在调用点使用已有的指定模型能力，或增加一层任务策略解析；这些用途配置是改造设计，不是当前源码已有的一组配置项。

Agent 主模型在 `AgentEngineConfiguration` 根据 `agent.chat.provider/model` 单独构建，不经过上述档位路由。第一阶段保持它不变，避免把工具层分流和 Agent 主模型替换混在一次改动里。

### LightRAG 需要在自己的服务里配置

Java 侧配置的是 LightRAG 服务地址与查询参数。该服务内部使用哪个 LLM、哪个 Embedding，要在服务自身的适配层和配置中确认。只修改 Java 的 `qwen3-local` 不会让外部 LightRAG 自动改用本地模型。

如果当前 LightRAG 版本只提供一套共享生成模型配置，修改它可能同时改变入库抽取和查询关键词提取。不能假设所有版本都支持按用途分开配置；需要确认版本能力，必要时增加适配函数或拆分部署职责。

### 超时与回退决定能否真正省钱

FAST 现有预算为 5 秒。本地模型在 GPU 繁忙或输入长时可能超过这个时间。如果先本地超时再请求云端，同一道题会消耗两边资源，用户还会等待更久。

分流方案应明确每种任务的输入上限、输出上限、超时、并发与失败处理。结构化结果无法解析可以有限回退；任务输入过长可以提前选择更合适的模型。所谓“低置信度回退”，也不能直接把模型自报的置信度当成可靠概率，需要校准或使用明确的质量信号。

短分类、改写通常不需要很长的思考输出。控制思考模式时要以所用推理服务的实际参数为准，不能认为 Java 请求里的 `thinking=false` 必然被所有兼容服务正确解释。

### Embedding 与 Rerank 先保持不变

当前别名 `qwen-emb-8b` 实际对应百炼 `text-embedding-v4`；本地候选对应 Qwen3 Embedding。两者不能因为同属 Qwen 或维度相同就混用。同一检索空间的文档与问题需要用匹配的嵌入模型。若更换模型，应重建相关向量，分别处理文档索引及图谱内部实体、关系和文本索引。

Rerank 当前使用百炼专用适配，不能假设任意本地重排端点都接受相同请求格式。首轮模型分流不改这两项，可以避免把生成模型的变化与检索表示变化混在一起，也避免为价格已经较低的服务承担额外迁移成本。

## 46.7 Token 与费用要用不同的公式

假设原来一次请求有 10,000 个云端 Token，分流后变成 6,000 个云端 Token 加 4,000 个本地 Token。云端付费 Token 降低 40%，总 Token 没有减少。如果本地输出更啰嗦，总 Token 甚至会增加。

对同一组问题，分别累计输入、输出、思考输出和重试消耗。用量字段的具体定义依供应商而定，避免把已包含在输出中的思考 Token 再加一次。

```text
云端付费 Token 降幅 = 1 - 改造后云端 Token / 基线云端 Token

单次云端费用 = 输入 Token × 输入单价 + 输出 Token × 输出单价
链路云端费用 = 所有云端模型调用费用之和，包含失败后已计费的调用

本地化收益 = 被替代的云端费用 - 新增回退费用 - 新增其他云端调用费用
系统总成本 = 剩余 API 费用 + 本地算力成本 + 运维与资源占用成本
```

Qwen-Flash 与 Qwen3-Max 的单价不同，输入与输出的单价也不同。因此迁移了 40% 的 Token，不代表节省了 40% 的钱。尤其当迁移的是廉价改写，而留下的是昂贵答案生成时，Token 降幅会高于费用降幅。

简历数字采用“云端 LLM 费用”口径，排除 Embedding、Rerank、建库、裁判和本地 GPU 成本。这个分母必须在面试时说清楚。

## 46.8 固定 RAG 的估算怎样得到

先看一个简化场景：单题、单个子问题、一次有效知识检索，图谱开启，无重试、缓存命中和历史摘要。本地承接改写、意图、图谱关键词提取，最终回答保留云端。

下面所有 Token 都是预算假设，不是从官方评测结果采样得到的平均值。

| 阶段 | 假设输入 Token | 假设输出 Token | 基线计价模型 | 改造后位置 |
|---|---:|---:|---|---|
| 改写拆分 | 1,500 | 150 | Qwen-Flash | 本地 |
| 意图识别 | 4,000 | 300 | Qwen3-Max | 本地 |
| 图谱关键词 | 500 | 150 | 假设为 Qwen3-Max | 本地 |
| 证据回答 | 8,000 | 800 | Qwen3-Max | 云端 |

基线合计 15,400 Token，其中拟迁移 6,600 Token，云端付费 Token 降幅约 42.9%。

按 2026-09-11 查询的百炼北京常规非缓存单价，Qwen-Flash 每百万输入/输出 Token 为 0.15/1.5 元；Qwen3-Max 在不超过 32K 输入档为 2.5/10 元。由此得到各阶段费用约 0.00045、0.013、0.00275、0.028 元，总计 0.0442 元。迁移前三项后剩 0.028 元，云端 LLM 费用降低约 **36.7%**。[价格来源](https://help.aliyun.com/zh/model-studio/model-pricing)

简历暂取 **25%–40%（估计，待实测）**，作为上述场景附近的规划区间，而非统计置信区间。比如答案增长到输入 12,000、输出 1,200 Token，其他不变，费用降幅变为约 27.8%。如果答案更短、意图树更长，迁移比例又会升高。该区间不保证覆盖任意业务负载。

相同口径下，云端付费 Token 可暂用 **30%–45% 的规划估计**；它与费用区间分别保留，不能相互替代。图谱关闭、关键词命中缓存、意图识别本来使用更便宜模型或本地频繁回退时，应重新估算。

## 46.9 Agent 为什么通常不能照搬固定 RAG 的比例

假设 Agent 为比较两款手机调用知识工具两次，然后组织答案。每次知识工具仍包含上一节的内部处理；除此之外，Agent 自己还有决策和最终回答的模型开销。

设知识工具单次基线费用为 S，可迁移费用为 L，调用次数为 k，Agent 外层云端模型总费用为 D：

```text
Agent 基线费用 = D + k × S
迁移辅助处理后的费用 = D + k × (S - L)
费用降幅 = k × L / (D + k × S)
```

沿用 S=0.0442 元、L=0.0162 元，并假设 k=2。如果外层 D 在 0.05～0.23 元之间，费用降幅约为 10.2%～23.4%。这就是简历暂用 **10%–25%（估计，待实测）** 的演算依据。

这里的 D 是敏感性分析参数，**不是对当前 DeepSeek 外层模型实际价格与用量的观测**。真实 D 应用每轮上下文、输出长度、缓存、供应商单价和重试记录计算。选择这个区间只是展示外层成本如何稀释工具内部的降本收益，不能将它当成已经预测准确的业务平均值。

Token 也可独立演算：两次工具内处理共 30,800 Token，其中 13,200 拟迁往本地。若外层 Agent 合计 26,000 Token，则云端付费 Token 降幅约 23.2%；外层在 15,000～50,000 Token 时，降幅约 16.3%～28.8%。可暂以 **15%–30%** 作为该负载附近的规划估计。

为什么 Agent 外层 Token 会大？下一轮模型往往要读已有的消息、工具调用和工具结果，历史随着执行增长。它不是“每轮只读当前的新问题”。不过源码还有裁剪、摘要和上下文预算，不能把历史增长无限外推。

这些公式也回答了一个反直觉问题：如果 Agent 根本不搜索知识库，k=0，本方案对这一请求可能几乎不省钱；如果大量重复搜索，辅助调用迁移收益可能更高，但还应先检查是否存在无效循环。固定调用轨迹的预算模型用于理解分母，真实评估不能强制新旧 Agent 走相同轨迹来掩盖行为变化。

## 46.10 为什么这个比例与整套评测降本不同

官方 runner 对每题请求 `/rag/v3/chat` 和 `/rag/eval`，后者会独立再走改写、意图与检索。它不是从同一次回答里直接复用完整证据快照。评分阶段还要支付 RAGAS 裁判的费用。当前 runner 也不是完整的 Agent 循环评测器。

因此存在三个分母：

| 口径 | 包含什么 | 本章简历百分比是否适用 |
|---|---|---|
| 固定 RAG 业务请求 | 一次问答中的文本 LLM 调用 | 适用，按本章假设估算 |
| Agent 业务请求 | 外层循环与工具内部文本 LLM | 适用，但必须带外层预算与工具轮次假设 |
| 官方评测整轮 | 回答、旁路重检索、裁判、向量与重排 | 不直接适用 |

此前 150 题约 50 元的演算，把裁判等开销计入总额。在那组假设里，辅助调用本地化只让整轮费用降低约 10%，与本章单次固定 RAG 的约 36.7% 不矛盾。两者分母不同。

第一阶段保留同一个云端裁判，是为了让改造前后的评分尺度一致。日常可以另用本地裁判筛选失败案例，但本地分数与云端分数应分开记录。不能因为便宜裁判给分更高，就宣称产品质量提升。

评测脚本还有一个接入细节：生成裁判与评测 Embedding 共用配置的 base URL。若仅将裁判生成迁至本地、Embedding 留在原服务，需要拆分配置或增加路由适配，不能只把一个 URL 换成本地地址。

## 46.11 怎样在将来补齐真实结果

现在不需要实际运行。等要把估算替换为简历成果时，至少记录下面这组对照信息。

先固定数据集、知识库快照、图谱版本、检索参数、云端主模型、裁判模型和上下文策略，再只替换辅助模型。固定 RAG 与 Agent 分别比较，图谱建库费用单独记录。Agent 评测要收集实际的工具次数与最终完成情况，不能仅把官方固定 RAG runner 改一个 URL 就认为覆盖完整。

每个模型调用至少关联请求 ID、用途、模型、云端/本地、输入与输出用量、耗时、回退、重试和结果状态。汇总时从同一批问题统计总费用、每题费用和每个成功任务费用，同时报告失败率。如果只算成功样本，可能把昂贵的失败重试隐藏掉。

质量方面，辅助任务检查改写约束保留、意图识别、JSON 成功率与摘要遗漏；业务侧检查召回、忠实度、回答正确性和 Agent 任务完成率。延迟方面区分单节点耗时、首字时间、完整完成时间与 GPU 排队。

最后才计算百分比：分别填云端输入 Token、云端输出 Token、本地 Token、API 费用和本地资源成本。新旧模型的 Tokenizer 可能不同，不能仅凭 Token 总数判断处理了同样多的内容。

可以先约定可接受的质量退化预算，再判断省钱是否值得。阈值需要根据任务确定，不能在没有测量前写“效果无损”。若本地导致更多检索轮次或错误回退，应将这些代价完整计入。

## 46.12 面试时怎样解释这项选择

**问：你为什么不把所有调用都转本地？**

答：我按任务难度和错误影响拆分。改写、意图和关键词处理依赖给定材料、输出范围明确，适合先用本地 Qwen；最终回答与 Agent 决策涉及证据融合和多步行动，第一阶段保留云端。这样可以先观察辅助层替换对效果和成本的影响，再决定是否迁移工具内答案生成。

**问：你说有 16 处调用，是每道题调用 16 次吗？**

答：不是，这是 Java 侧文本模型的静态业务入口数量。每道题的动态次数取决于拆分、分支、工具轮次和摘要条件。外部图谱、评测裁判另算。真实降本统计以调用记录为准，不用静态入口数当调用次数。

**问：Token 是怎么省下来的？**

答：这里主要减少云端付费 Token，把一部分计算转到本地；并不保证总 Token 减少。摘要和工具结果裁剪才是另一类可能减少后续输入总量的机制，不能把两项收益混算。

**问：为什么是 Qwen？8B 一定够吗？**

答：项目已有本地 Qwen 的候选与兼容接口，接入成本低，中文受约束任务值得验证。但模型规模要用结构化输出、意图和摘要质量、延迟、显存共同决定。我会从较小模型开始比较，不把“能加载”当成“足够完成任务”。

**问：意图识别错了怎么办？**

答：先校验标签和输出结构，记录路由与召回结果；对不可解析等明确错误做有限回退。语义分类错误不能只靠 JSON 校验发现，需要离线标注和下游检索指标。如果某类意图持续退化，可以只把这类任务保留云端。

**问：为什么固定 RAG 和 Agent 节省比例不同？**

答：固定 RAG 主要是辅助处理加一次答案生成；Agent 除工具内部处理，还有不迁移的外层模型循环。工具里省下同样的钱，占 Agent 总预算的比例通常更低，具体取决于工具调用次数和外层上下文。

**问：本地肯定比 API 便宜吗？**

答：不一定。轻任务的云端模型本身便宜，低频请求可能不值得独占 GPU。本地方案应在稳定批量负载和已有算力条件下评估，并计入电费、运维、排队与其他任务的机会成本。

**问：现在这些百分比是什么性质？**

答：目前是基于调用路径、假设 Token 和价格的规划估算，改造尚待实施与验证。固定 RAG 暂取 25%～40%、Agent 暂取 10%～25%的云端 LLM 费用区间；只有完成同条件实验后，才替换成实际成果数字。

## 简历条目与后续替换

当前待验证版使用以下文字，保留了实施状态与估算标记：

> 模型分流（拟实施）：梳理 16 处文本 LLM 调用入口，拟将改写、意图识别、图谱关键词提取与摘要分配至本地 Qwen，保留云端回答和 Agent 决策；固定 RAG / Agent 云端 LLM 费用预计降低 25%–40% / 10%–25%（估计，待实测）。

完成改造和实验后，才把“拟实施／拟将／预计／估计”替换为实际状态和结果。若要补 Token 指标，应写“云端付费 Token”，并分别标注两条链路；不要为塞进一条简历同时堆叠入口数、调用数、Token、费用、延迟和质量六组指标。
