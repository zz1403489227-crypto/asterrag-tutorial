# 第 21 章：HNSW——给向量修一张能快速找路的地图

> 本章先讲“索引为什么有用”，再一步步建立 HNSW，最后跟随一个问题走完查询。读完应当能画出建图和查图过程，而不只是记住 HNSW 的名字。

## 21.1 我们究竟在找什么

先准备一组贯穿后面五章的教学资料：

| 资料 | 内容 |
|---|---|
| 人员记录 | 林辰是远山科技的外包工程师，目前参与星河项目。 |
| 项目介绍 | 星河项目的负责人是周宁。远山科技为该项目提供研发支持。 |
| 外包差旅规定 | 外包人员因项目出差，差旅费用由所在项目的负责人审批。 |
| 普通员工规定 | 正式员工的差旅费用由直属经理审批。 |

用户问：“星河项目的外包工程师林辰出差，费用应该找谁审批？”这组人名、文档和后续数字用于教学，后面不再重复说明。

回答需要先找到相关材料。项目已经把文档分成片段，并为每个片段生成了 Embedding。Embedding 就是用一组数表示文本，使意思相近的文本倾向于落在相近的位置。用户的问题也会转换成同一空间中的向量。

于是，“找与问题有关的文字”变成了一个可计算的问题：**在许多片段向量中，找到离问题向量较近的那些。**

例如，“找谁审批”和“由项目负责人批准”用词不同，但意思接近，向量检索有机会把它们关联起来。向量的作用是提供这种比较方式；HNSW 的作用，是让这场比较不必每次都遍历所有片段。

## 21.2 索引是什么：把每次重复的工作提前做好

先不用任何索引。假设知识库有一百万个片段，每个向量有 1536 个维度。

一次查询可以这样做：计算问题向量与第一个片段的距离，再计算第二个，直到一百万个全部算完，最后选出最近的十个。这叫精确近邻搜索。距离计算量大致随“片段数量 × 向量维度”增长。

这相当于找一本书时，每次都从图书馆第一排开始看书脊。虽然能找到，但重复劳动很多。

索引的思路是：**资料入库时，多花一些时间建立辅助结构；查询时利用这份结构，缩小需要检查的范围。**

字典按拼音排序、数据库为某列建立查找结构、搜索引擎记录哪些文档含有哪些词，都是这一思想的不同应用。索引并不替代原数据，它保存的是帮助你更快到达原数据的线索。

对高维向量而言，HNSW 选择保存“从一个向量走向哪些向量”的导航关系。你可以把它理解成一张专门为近邻搜索修建的路网。

## 21.3 第一步：让相近向量之间有路可走

先不考虑分层，只想象一张图：每个节点是一个片段向量，边连接一些适合导航的邻居。

如果问题向量靠近 J，而当前入口在 A，算法会计算 A 周围几个邻居到问题的距离，选择更值得探索的方向，再继续查看下一批邻居。

为什么这可能比全量比较快？因为每次移动都利用了已有的邻近关系。问题大致属于“费用制度”区域时，搜索不必平均地检查所有招聘、财务、运维和产品说明。

但只连非常近的邻居会产生一个问题：虽然每一步方向大致正确，却可能要经过很多小步才能跨过整张图。就像一个城市只有小区道路，没有快速路，从城市一端走到另一端会很慢。

因此，好的近邻图既需要局部连接，也需要能把搜索引向其他区域的连接。HNSW 在选择邻居时还会考虑连接的分散程度，避免把有限的边全部挤在一个很小的方向上。

这时，我们已经得到第一层直觉：**图的作用不是储存业务关系，而是告诉搜索过程“接下来值得去哪里看看”。**

## 21.4 第二步：建立层次，上层赶路，下层细找

HNSW 的 H 是 Hierarchical，即分层。可以把其结构想象成下面这样，图中只画了部分导航连接：

```text
第 2 层： A ---------------------- H

第 1 层： A -------- D ----------- H -------- L

第 0 层： A -- B -- C -- D -- E -- F -- G -- H -- I -- J -- K -- L
```

底层包含全部节点；越往上，节点越少。同一个节点如果出现在高层，也会出现在它下面的各层。少量上层节点提供粗粒度导航，底层则提供细粒度搜索。

这里的层数不是按“人事库、财务库、技术库”划分的。插入节点时，算法会随机决定它能够到达的最高层，层数越高，出现概率越低。大量节点只在底层，少数节点出现在高层，路网因此自然形成层次。[HNSW 原论文](https://arxiv.org/abs/1603.09320)

为什么这样有用？假设问题靠近 J：

1. 在最上层，比较 A 和 H，就可能快速移动到 H 附近。
2. 下降一层，在 H 周围继续定位，不必从 A 重新开始。
3. 到底层，从已经不错的入口出发，详细比较 I、J、K 等附近节点。

一层一层下降，是把“大范围定位”和“局部精找”拆开。这也是分层结构真正提供的价值，而不是单纯多保存几份图。

## 21.5 这张图怎么建立：一个新片段的入库过程

现在假设新来了一个向量 X。已有图中存着许多旧片段，X 需要接入这张图。

建图可以分成四步理解。

**第一步，决定 X 出现在哪些层。** 随机产生 X 的最高层。例如结果是第 1 层，那么 X 会出现在第 0、1 层，而不会出现在第 2 层。

**第二步，找到 X 大致应该接入的区域。** 从已有图的高层入口开始，用“到 X 的距离”导航，逐层走到合适位置。注意，此时 X 相当于一次查询的目标；建图本身也复用了搜索过程。

**第三步，在需要插入的层里找一批候选邻居。** 不只找到一个最近节点就停，而是先探索若干候选，再选出适合连接的邻居。邻居数量受到预算约束，不能把 X 与所有旧节点都连接，否则索引的存储和维护成本会过高。

**第四步，连边并维护邻居列表。** 将 X 与选中的节点建立导航连接；已有节点的连接数如果超出预算，就要筛选、裁剪。若 X 的最高层高于当前入口层，还会更新高层入口。

```text
新片段 → Embedding → 新向量 X
                         ↓
                    随机确定层高
                         ↓
                 用现有图寻找插入区域
                         ↓
                   搜索并选择邻居
                         ↓
                    连边、修剪连接
                         ↓
                    X 加入索引
```

因此，HNSW 是逐步长出来的索引。新增文档主要是把新向量加入已有结构，不需要每次都把全库推倒重建。建图比直接存一行数据多做了工作，换来的好处留给了以后的多次查询。[hnswlib 算法实现](https://github.com/nmslib/hnswlib/blob/master/hnswlib/hnswalg.h)

## 21.6 查询为什么不能每次只保留一个“看起来最近”的节点

只盯着当前最近的节点，可能过早放弃其他方向。某条路眼下略远，却可能通向更近的区域。

因此，HNSW 的底层搜索会保留一组有希望的候选。理解它时，可以在脑中放两份集合：一份记录还值得展开的节点，另一份保留目前找到的较好结果。每次优先展开更有希望的节点，检查其邻居，再更新这两份集合。

下面只演示距离与候选变化。假设当前从 H 开始，搜索保留宽度暂取 3：

| 动作 | 新观察到的距离 | 当前较好的三个候选 |
|---|---|---|
| 到达 H | H=0.40 | H |
| 展开 H | G=0.60，I=0.12，L=0.30 | I、L、H |
| 优先展开 I | 发现 J=0.10 | J、I、L |
| 继续检查有希望的方向 | 没有找到更好的结果 | J、I、L |

如果用户只要两条，最后从保留结果中取 J、I。**“搜索过程中保留三个候选”和“最终返回两条”是两件事。**

实际实现通过候选队列、距离界限等条件判断是否继续展开。理解上的关键是：它不是随机乱走，也不是把整张图遍历一遍，而是在有限搜索宽度内不断保留更值得探索的方向。

这也解释了为什么 HNSW 是近似搜索：一些方向会被剪掉，真正最近的节点可能恰好在被放弃的路径后面。增加搜索宽度能够投入更多计算来争取更充分的近邻召回，但不会把“语义相近”自动变成“答案正确”。

## 21.7 三个参数其实是在分配三种预算

记参数名之前，先记住它们控制的工作：

| 参数 | 控制什么 | 调大通常意味着什么 |
|---|---|---|
| `M` | 每个节点的连接预算 | 路更多，图更占内存，构建维护更贵 |
| `efConstruction` | 建图时找邻居的候选宽度 | 建图时更认真找路，构建耗时增加 |
| `ef_search` / `ef` | 查询时保留的搜索候选宽度 | 查得更充分，单次搜索计算增加 |

它们分别回答“修多少路”“修路时多认真选邻居”“查找时愿意探索多少方向”。这比死记 48、200 等数字更有用。[hnswlib 参数说明](https://github.com/nmslib/hnswlib/blob/master/ALGO_PARAMS.md)

另有一个由业务决定的 topK：最后要返回多少片段。即使最后只需要 10 条，也可能在搜索时探索和保留更多候选。先多找、再精选，是后面整个 RAG 检索漏斗反复出现的思想。

## 21.8 余弦距离在这里负责什么

向量可以按不同方式定义“近”。本项目默认 PG 路径使用余弦距离，它比较两个向量方向的一致程度。

```text
余弦相似度 = 两向量点积 / 两向量长度的乘积
余弦距离   = 1 - 余弦相似度
```

方向越一致，相似度越大，距离越小。把向量整体乘以正数会改变长度，却不改变余弦相似度。

这和 HNSW 是两个层次：距离函数是衡量每一步好坏的尺子；HNSW 是拿着这把尺子寻找邻居的路线策略。更换尺子可能改变谁是邻居；更换索引则改变怎样找邻居。

## 21.9 为什么还要关心知识库过滤

在我们的例子里，搜索目标是星河项目相关资料。即使数据库中有很多“出差审批”片段，其他项目的规定也不一定适用。

检索因此不只有“谁最近”，还有“哪些片段属于允许搜索的范围”。当近邻索引找到的一批候选中，很多被范围过滤排除时，最终留下的条数就会减少。查得更深入，可以继续寻找范围内的候选。

这解释了项目为什么既有按知识库筛选，也有搜索宽度和迭代扫描设置。前者限定证据范围，后者改善近邻搜索的充分程度。它们共同影响召回，但职责不同。

## 21.10 项目怎样用上整套机制

现在回到项目，代码只需要落在两条清楚的链上：

```text
入库：文档 → 分块 → Embedding → 写入 pgvector → 数据库维护 HNSW
查询：问题 → Embedding → 按库范围做余弦近邻搜索 → 返回候选片段
```

默认向量后端是 PostgreSQL + pgvector。表中的 `embedding vector(1536)` 保存数值，HNSW 索引声明是：

```sql
CREATE INDEX idx_kv_embedding ON t_knowledge_vector
USING hnsw (embedding vector_cosine_ops);
```

查询按下面的核心形式表达：

```sql
SELECT ...
FROM t_knowledge_vector
WHERE collection_name IN (...)
ORDER BY embedding <=> ?::vector
LIMIT ?;
```

`<=>` 表示余弦距离。项目把它交给数据库执行，HNSW 算法由 pgvector 提供；业务代码不需要自己管理图中的每条边。[pgvector 索引与查询](https://github.com/pgvector/pgvector#hnsw)

至此可以把职责说完整：Embedding 把文本变成可比较的位置；HNSW 帮助高效找到附近位置；数据库返回对应片段；后面的排序和生成再判断这些片段是否足以回答问题。

## 21.11 把本章压缩成一句原理

> HNSW 在入库时把向量组织成分层邻近图，查询时先在稀疏高层快速定位，再在底层保留多个候选细找，用额外的建图和存储成本换取更少的查询比较。

回到林辰的审批问题，HNSW 能帮助我们更快找到“出差审批”附近的片段，却不一定把“星河”“外包”这些关键条件排到最前。下一章的 BM25 将从词面匹配补充这个观察角度。
