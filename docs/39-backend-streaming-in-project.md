# 第 39 章：一段回答怎样流出来，又怎样结束干净

> 第一部分 · 项目应用。面经入口：SSE 高并发、线程池、任务异常、线程终止、线程安全。

配套问答：[AgentRunHandle 与唯一收尾](45-agent-request-study-qa.md#finalization) · [从网络帧理解 SSE](45-agent-request-study-qa.md#sse) · [冻结版与新上游的确认/重试差异](45-agent-request-study-qa.md#version-diff)。

## 39.1 Controller 返回了，不代表回答结束了

普通接口大致是“算出完整结果 → 返回 JSON → 请求完成”。Agent 回答可能等待检索、多次模型调用和工具执行，用户又希望尽早看到第一段文字。SSE 让服务器在一条 HTTP 响应上持续发送事件。

项目使用 Spring MVC 的 `SseEmitter`。`AgentChatController` 创建 Emitter，调用服务启动处理，再把 Emitter 返回。注意服务调用发生在 return 之前，取得闸门、建立会话等启动步骤不是凭空变成异步。之后订阅 Agent 事件流，增量事件继续向这个响应写入。

Servlet 异步处理允许初始请求线程退出而响应保持打开，但不代表网络写入、数据库访问和模型调用全部变成非阻塞。看到 Reactor `Flux` 也不能断言项目服务器就是 WebFlux。[Spring MVC 异步与流式响应](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html)

## 39.2 模型事件为什么不能直接扔给前端

AgentScope 提供框架事件，前端需要稳定的产品协议和历史展示。因此中间有每轮独立的 `AgentStreamEventBridge`：

- 文本增量进入回答缓冲区，并转换成前端消息增量。
- 思考和工具事件更新本轮轨迹块，让页面知道某工具是否仍在运行。
- 正常完成时确定最终内容，保存助手消息，发 finish 和 done。
- 取消时保存已有正文或轨迹，标为 INTERRUPTED，再发 cancel 和 done。

没有流式增量但 Agent 最终结果有正文时，还会补发一次正文。这解释了为什么不能仅凭“有没有收到若干 delta”判断模型是否产生答案。

`SseEmitterSender` 封装连接关闭状态，发送异常时记录并尝试异常结束。它的 `closed` 只表示连接层状态，不表示数据库消息已写成功，也不表示 Agent 业务句柄已经完整释放。

## 39.3 三个结束信号可能同时到来

假设模型即将完成，用户点了停止，网络也恰好断开。事件桥收到 onComplete，任务管理器触发取消 finalizer，Emitter 又触发 onError。若三条路径都直接插入助手消息、释放闸门、清理任务，就可能重复结束或相互干扰。

`AgentRunHandle` 用 `AtomicBoolean settled` 控制收尾入口：

```text
正常 / 取消 / 异常
          ↓
compareAndSet(false, true)
          ↓
只有成功者执行该路径的结束动作
          ↓ finally
注销任务 → 执行释放钩子
```

普通布尔变量的“先判断再赋值”是两个动作，两个线程可能同时读到 false；CAS 把条件判断和状态改变合为原子竞争，只有一个能把 false 改成 true。

这里保证的是**本轮句柄的收尾入口至多执行一次**。它不是跨进程 exactly-once，也不保证结束动作一定成功。标志先置为已结算，数据库插入随后可能失败；代码没有把标志重新设回 false 自动重跑整轮收尾。

具体到冻结版的助手消息写入，`persistAssistantMessage` 自己捕获异常并返回 null，正常收尾体仍可能发送 messageId 为 null 的 finish 与 done。因此“收到结束事件”和“刷新后能查到已持久化消息”也必须分开判断。另一个版本边界是：本版 `onError` 记录错误后异常关闭通道，没有较新上游的中断消息落库与 finish/done 路径。

为什么 finally 重要？因为即使业务结束动作出异常，任务注册与闸门仍需要释放。否则用户可能明明看到失败，却一直被“正在运行”挡住。

## 39.4 CAS、synchronized、volatile 各保护什么

不要用“项目用了线程安全机制”一句带过。这里有三个不同问题。

**单个终态竞争，用 CAS。** `settled` 只需要从未结束变成已结束，适合一次状态抢占。

**多个相关字段一起操作，用锁。** 事件桥的回答缓冲区、思考缓冲区和轨迹快照涉及复合读写，因此通过 `stateLock` 保护相应临界区。RunHandle 的释放钩子集合和 released 标志也在同一把锁下检查、复制和清空，确保“登记钩子”不会漏在“已经释放”之后。

**跨线程发布句柄，用 volatile。** 订阅句柄和中断函数可能后绑定、先收到取消；volatile 让另一个线程能看见新引用。它不负责把多个字段的修改变成一个整体事务。

释放钩子在锁内取快照，真正执行在锁外。这样不会拿着内部锁长时间访问 Redis 或执行其他清理逻辑。每个钩子异常单独处理，也避免第一个钩子失败后其余钩子全不执行。

## 39.5 超时、取消订阅、线程中断是三回事

多通道检索用 `CompletableFuture.supplyAsync` 把已启用通道交给 `ragRetrievalExecutor`，对 Future 设置超时，异常/超时转成通道空结果，然后继续融合。前提是这些通道实际启用，不是默认一定三路并行。

`orTimeout` 决定调用方等待结果到什么时候，不自动证明底层 HTTP/数据库操作已经停掉。底层还需要自己的连接、读取或查询超时。否则上层不等了，后台仍可能占着线程和连接。

Agent 停止路径会 dispose 订阅，再尝试调用 Agent interrupt。取消是协作过程：不再接收后续事件、请求运行时中断、外部工具是否支持停止，属于不同层。不能从一次 `dispose` 推导“供应商立即停算、绝不继续计费、外部写操作撤销”。

## 39.6 线程池为什么分开，而不是全用一个

实际配置为不同工作提供线程池：通道检索、检索内部任务、MCP 批处理、意图识别、模型流输出等。这样可以表达不同容量与拒绝策略，降低慢任务占满同一个队列的风险。

例如通道检索池的核心和最大线程数都是 CPU 数的 4 倍，队列使用 `SynchronousQueue`，拒绝策略是 CallerRunsPolicy。这个队列不储存一大批等待任务，而是直接交接；工作线程都忙时，提交者可能自己执行任务，形成反压。

模型流输出池使用容量 200 的队列和 AbortPolicy，饱和时抛拒绝异常。不同策略有不同失败表现，不能说“线程池满了都会自动排队”。此外 CallerRuns 可能让原本负责派发任务的线程被慢工作阻塞，连带推迟后续派发；配置存在不等于所有时刻都能获得理想并行度。

这些是源码配置，不是性能最优结论。合理大小取决于模型和数据库的容量、任务等待时间、连接池大小及峰值负载，不能只靠“CPU 数乘四”推导系统吞吐。

## 39.7 为什么答案结束后还会有工作

运行释放钩子中会按配置安排长期记忆提取。它捕获该用户和会话，放到 Reactor 的 boundedElastic 调度器执行；异常记录日志。这里用的是另一条后台异步路径，不应该把项目所有异步都归到 `modelStreamExecutor`。

好处是不用等长期记忆抽取完成才结束用户回答；代价是回答结束和记忆更新之间有时间差，后台失败也不会把已经发出的回答回滚。面试谈“异步提高体验”时，应紧接着说清这种完成语义。

## 39.8 如果评测里出现“慢”或“失败”，怎么落到这一章

理想诊断把时间拆为接入/闸门、历史读取、检索等待、模型首字、工具耗时、持续生成、收尾持久化。先定位时间花在哪里，再决定检查线程池、连接池、数据库计划或模型供应商，而不是看到 SSE 就先加线程。

另外分别统计连接结束、Agent 结束、助手落库、后台记忆完成。某一层成功不能替代其他层成功。观测设计可沿用第 32～34 章，这里不宣称这些分段指标都已经部署。

面试可用一句话收束：“我把运行结束和连接关闭分开管理，用每轮句柄的 CAS 统一业务收尾，锁保护输出快照，volatile 发布取消句柄；超时控制等待预算，真正停止还要依赖底层协作。”
