# 第 42 章：从会话查询出发，理解索引、SQL 和事务

> 第二部分 · 基础追问。面经中 MySQL 问题很多，本项目使用 PostgreSQL；先讲共通原理，再明确具体实现差异。文中演算数据和候选 SQL 都是教学示例，没有执行数据库查询。

## 42.1 索引为什么有用，为什么又有代价

假设消息表有很多行，你要找林辰某个会话的消息。没有合适索引时，数据库可能扫描很多数据页，逐行检查条件。索引把某些键组织成更便于定位的结构，让数据库尽量少访问无关数据。

代价是索引自己占空间，插入、更新和删除时也要维护；更多索引还可能增加缓存压力。索引不是“加得越多越快”，而是用写入与存储成本换取特定读路径的效率。

最重要的区分：**有索引、优化器选择索引、索引扫描范围小、查询真的快，是四个不同结论。**

## 42.2 为什么常用 B+ 树思想，而不是二叉树或哈希

B+ 树把多个有序键放在一个节点中，内部节点指引搜索，叶子层保存索引条目并支持有序遍历。高扇出使树比较矮，访问一条数据时需要走的层数较少；范围查询定位起点后可以沿有序叶子继续扫描。

二叉树每个节点分支少，在面向页的存储中通常需要更多层；哈希擅长等值定位，但不天然维护全局顺序，因此不适合直接服务范围和排序。数据库选择索引结构，要看访问模式，不是看哪个数据结构名气更大。

注意索引叶子“指向什么”取决于数据库实现。面经常说的 InnoDB 聚簇主键索引叶子保存整行、二级索引叶子保存主键，是 MySQL/InnoDB 的具体组织。PostgreSQL 常规表存储为 heap，B-tree 索引条目定位 heap 元组；不能原样套用“所有二级索引再回主键树”的叙述。

## 42.3 联合索引 (a,b,c)，a=1 且 c=1 到底能不能用

先把联合索引理解为字典序：先按 a 排，a 相同时按 b，b 也相同时按 c。

```text
(1, 1, 1)
(1, 1, 9)
(1, 2, 1)
(1, 2, 8)
(2, 1, 1)
```

条件 `a=1 AND c=1` 能先定位 a=1 的区域，但 c=1 分散在不同 b 组里，不是这个区域中单一连续小段。所以不能答“缺 b 整个索引完全失效”，也不能答“三列都充分用于快速定位”。要分别问：能否用 a 限定范围，c 在哪里过滤，是否还需大量扫描或回表。

同理 `a=1 AND b>3 AND c=1` 中，b 的范围改变了后续列对连续扫描边界的作用，c 可能仍用于过滤。具体数据库版本可能有跳跃扫描等优化，不要把口诀说成跨版本绝对规则；最终看计划与数据分布。这里用 PostgreSQL 17 的多列 B-tree 规则作为解释基准，不冒充已核验部署版本。[多列索引说明](https://www.postgresql.org/docs/17/indexes-multicolumn.html)

**回到项目：** 会话 `(user_id,last_time)` 可以先定位一个用户再按时间访问；消息 `(conversation_id,user_id,create_time)` 与实际 `ORDER BY id` 不相同，过滤有帮助不代表顺便消除了 id 排序。

## 42.4 哪些情况“有索引仍然慢”

先从输入、查询和代价三个层次判断。

输入层：条件命中半张表，使用索引加大量随机访问可能不如顺序扫描。查询层：对列做不匹配的函数、类型转换、排序表达式，或要求索引不擅长的匹配，可能无法利用已有结构。代价层：统计信息不准、返回字段太多、深分页、额外排序与连接等待，都可能主导耗时。

`LIKE '%报销%'` 不是普通 B-tree 擅长的前缀定位，不能从这里直接推出“所有 LIKE 都不能用索引”。前缀匹配还涉及排序规则与算子类；全文相关性则应讨论倒排索引，而不是硬把任意文本搜索塞给业务 B-tree。

覆盖索引也要区分数据库。PostgreSQL 即使索引含查询所需列，还要看可见性信息是否足以避免 heap 检查；不是“SELECT 字段都在索引里就绝不会访问表”。[PG Index-Only Scan](https://www.postgresql.org/docs/17/indexes-index-only-scans.html)

## 42.5 慢 SQL 应该怎样分析，而不是上来建索引

以“打开会话历史慢”为例，理想排查顺序是：

1. 确认慢的是等数据库连接、执行 SQL、返回大量结果，还是服务端组装/网络传输。
2. 找到实际 SQL 和参数范围：是不是忘了 userId、是否一次加载全部历史、有没有 N+1。
3. 看执行计划中的扫描方式、过滤条件、估算行数、排序与连接节点。
4. 允许实际诊断时再比较实际行数/耗时/缓冲区访问与估计；判断统计失真还是访问路径不合适。
5. 提出查询改写、分页、候选索引等方案，并考虑写入与存储成本。

`EXPLAIN` 展示计划，`EXPLAIN ANALYZE` 会真正执行语句；面对修改语句尤其不能把它当只读查看按钮。本教程不执行这些命令。[PostgreSQL EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html)

若设计历史分页，可以按消息游标读取，例如在可信身份范围内加 `id < :lastId ORDER BY id DESC LIMIT :pageSize`，而不是 OFFSET 越翻越大。但要确认 id 的排序语义与产品展示一致；相同时间戳分页通常需要稳定的第二排序键。上面的参数符号是教学表达，不是本项目新增接口。

## 42.6 ACID 不要背成四个形容词

用删除会话解释：

- 原子性：同一事务中的会话、消息、状态删除作为一个数据库单元提交或回滚。
- 一致性：事务前后满足定义好的约束和业务不变量，例如有效会话唯一；数据库不会替你发明所有业务规则。
- 隔离性：并发事务互相看见什么、哪些操作会等待，由隔离级别与锁等机制约束。
- 持久性：已经确认提交的数据如何在故障后保存，依赖 WAL、持久化设置和存储保障。

“一致性”不是说 Redis、模型供应商、浏览器也被这个 SQL 事务原子覆盖。第 37 章的 afterCommit 清理正好说明外部状态的另一个边界。

## 42.7 MVCC 为什么能让读写并发

直觉上，如果更新一行就覆盖唯一副本，读者只能等写者结束，或冒险看到中间状态。MVCC 通过版本和可见性规则，让读者根据自己的快照判断该看哪个版本。

设会话标题原来是“上海”，事务 A 把它改成“上海出差”，但尚未提交。事务 B 的普通读取不会直接把这个未提交标题当成事实。A 提交以后，B 后续是否看见新标题，取决于隔离级别和读取时点。

PostgreSQL 默认 Read Committed 下，每条语句取得新的快照，同一事务的两次 SELECT 可能看到中间已提交的变化；Repeatable Read 主要基于事务快照，提供稳定可见性，但仍不能替代所有业务约束；Serializable 还要处理序列化失败并重试整个事务。PG 的 Read Uncommitted 实际按 Read Committed 处理，PG Repeatable Read 不出现 SQL 标准表中允许的那种幻读，也不能因此说等价于可串行化。[PG 隔离级别](https://www.postgresql.org/docs/17/transaction-iso.html)

不要把 MySQL 的 undo 版本链、间隙锁等所有细节照搬到 PostgreSQL。PG 的旧元组版本需要清理，VACUUM 回收可复用空间并承担可见性、冻结等维护；长事务可能延迟旧版本回收，导致膨胀。普通 VACUUM 也不是保证把整个表文件立刻缩小还给操作系统。[PG VACUUM](https://www.postgresql.org/docs/17/routine-vacuuming.html)

## 42.8 乐观锁、悲观锁和丢失更新

假设两个更新者都读到版本 3，一个把标题改为“上海出差”，另一个改为“报销咨询”。直接无条件覆盖，后提交者可能覆盖前者，这是需要业务判断的冲突。

乐观控制可以用 `UPDATE ... SET ..., version=version+1 WHERE id=? AND version=?`，受影响行数为 0 表示版本冲突，再决定重试或提示。悲观控制可以在事务中用合适的行锁先锁住目标，其他竞争修改等待。一个主要在提交修改时检查冲突，一个提前协调竞争，适用场景不同。

PostgreSQL 行锁不会阻止所有普通 MVCC 读取；锁竞争、锁顺序和事务长短决定等待。死锁时数据库可能中止一个事务，业务需要识别并合理重试。[PG 显式锁](https://www.postgresql.org/docs/17/explicit-locking.html)

项目的状态 upsert 解决唯一键冲突，不自动实现以上 version 乐观锁；Redis 运行闸门减少特定运行竞争，也不代替数据库对所有写入口的约束。

## 42.9 WAL、redo/undo/binlog，怎么避免答串

WAL 的核心是先把恢复所需日志按要求写入持久存储，再依赖后续数据页落盘；崩溃后可以根据日志恢复，而不要求每次提交都把所有脏数据页立即写回。准确持久性仍取决于配置。[PG WAL](https://www.postgresql.org/docs/17/wal-intro.html)

面经若直接问 MySQL，可以概括 redo 用于崩溃恢复，undo 服务回滚和版本读取，binlog 记录服务器层变更、用于复制等；但说回项目时应切回 PostgreSQL 的 WAL、MVCC 元组和逻辑解码，不要回答“我们 PG 监听 binlog”。本项目索引同步目前不是 CDC，前文已经展示真实装饰器链。

## 42.10 B-tree、GIN、HNSW、ES 倒排，怎样放在同一张脑图里

| 要问的问题 | 需要的数据组织 | 项目落点 |
|---|---|---|
| 某用户最近有哪些会话 | 有序标量键 | PG 会话 B-tree |
| JSON 文档是否含某些键值条件 | 从成分找包含它的行 | metadata GIN，具体看操作符 |
| 哪些段落语义接近当前问题 | 高维近邻结构 | pgvector HNSW |
| 哪些段落与词项相关 | 词项到文档/位置等信息 | ES 倒排与 BM25，默认关闭 |

HNSW 是图结构的向量索引，不等于 LightRAG 的知识图谱。前者节点通常是向量，连边帮助近邻搜索；后者节点和关系表达实体及其语义关联。面试官从“索引”跳到“图谱”时，先划清这个概念层级，再回到第 21～23 章展开。
