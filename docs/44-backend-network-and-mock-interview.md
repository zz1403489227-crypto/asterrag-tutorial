# 第 44 章：从 SSE 接到网络、容量和完整面试追问

> 第二部分 · 基础追问。最后把后端重新接回 Agent/RAG 与评测，不继续扩散成与简历无关的后端百科。

## 44.1 SSE、WebSocket、轮询该怎么选

普通轮询是客户端反复问“有新结果了吗”，简单但有额外请求与等待；长轮询延长一次等待，有结果后再建立下一次。SSE 在一条 HTTP 响应里由服务器持续发事件；WebSocket 建立双向消息通道，适合持续双向交互。

文本问答的主要方向是服务器持续输出，用户提问和停止可以分别使用 HTTP 接口，因此 SSE 与项目需求吻合。若是需要持续双向音频或高频交互的实时系统，应重新比较传输方案；不能简单说 WebSocket 更高级，或 SSE 一定更快。

SSE 协议使用 UTF-8 文本，事件通过空行分隔，可有 event、data、id 等字段。下面是协议演示，不是当前产品新增事件：

```text
event: answer
id: 7
data: {"text":"住宿费标准需要根据城市等级判断。"}

```

网络读取的一块字节不一定等于一个完整事件，也不等于一个 token。前端需要缓冲并按协议解析，不能每次 read 就 JSON.parse 整块数据。[SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)

## 44.2 TCP 保证可靠，为什么应用还会丢回答

TCP 提供连接内有序可靠的字节传输，不提供应用级消息事务。浏览器可以收到一半响应后断线，数据库也可以在文本已经发送后落库失败；TCP 不会替你回滚屏幕上的文字或补写助手记录。

因此要分三层：传输有没有成功送达、业务有没有完成、结果有没有持久化。TCP 的字节流还需要 SSE 这样的应用层格式划分消息，不是“有 TCP 就自带 event 边界”。

如果问 TCP 与 UDP，可以从有序可靠字节流、连接状态和重传，与数据报边界和不同可靠性需求对比；不用在这一项目主动展开所有拥塞控制算法。把话题接回“为什么断线后需要应用层恢复设计”更有价值。

## 44.3 重连为什么不是继续生成，也不是业务幂等

原生 EventSource 有重连与 Last-Event-ID 机制，但服务端需要保存可恢复事件、解释事件编号并提供重放，才可能从已知位置继续交付。使用 fetch 自行解析事件流的客户端又有自己的重连逻辑。协议具备字段，不代表项目已经实现完整断点续传。

项目应按当前前端与后端行为解释：重新发起问答和恢复同一轮输出不是同一件事。新请求若生成新 taskId，就可能重新走 Agent、重新调用工具。

对带副作用的工具，理想做法是另设业务幂等键，把业务操作身份与 HTTP 重试次数分离，并持久化操作状态。运行闸门只阻止某一时刻并发运行，旧任务释放以后，同一个问题仍可再执行；它不是永久的“同一句话只做一次”。

## 44.4 GET / POST 与鉴权有什么值得注意的

冻结 Agent 提问接口使用 GET，停止接口使用 POST。按一般 HTTP 语义，GET 应面向安全读取；这里提问会创建运行和消息，因此谈改进时可说明使用 POST 发起运行、再订阅事件的设计理由，而不把当前实现改说成 POST。

问题放在 URL 查询参数中还涉及日志、历史和代理可见性，不能默认所有链路都会自动脱敏。HTTPS 保护传输过程，不会阻止服务端自己记录敏感 URL。

登录验证是“你是谁”，资源授权是“你能否操作这个会话/任务”。CORS 是浏览器跨域访问机制，不是服务端访问控制；把接口隐藏在前端页面之外，也不等于没有权限的人不能直接请求它。项目查询和取消的 owner 检查，是应当重点讲的授权例子。

## 44.5 SSE 并发量应该怎么估计

先区分吞吐与并发。假设理想稳定场景每秒到达 5 个问答，每轮平均保持 20 秒，平均在途规模约是 `5 × 20 = 100`。这是 Little 定律的教学估算，不是项目测试数据；突发和长尾还会让峰值更高。

这些在途请求占的不只有请求线程，还包括连接、Emitter、本轮缓冲区、任务表、模型调用配额和可能的数据库/HTTP 连接。异步释放初始线程，不代表每条长连接零成本。

若每轮平均要调用模型两次，并发预算又要考虑多次调用和不同阶段重叠。线程池、模型并发、连接池和全局准入要协同，不能让上游无限接收再在下游堆积。

用户闸门限制每用户一轮，不是系统总容量保护。若有很多不同用户同时进入，仍需要独立的全局容量设计。题库问“异步框架高并发瓶颈”时，按资源链回答，比只谈语言快慢更能体现理解。

## 44.6 超时和重试，怎么避免把故障放大

一次 Agent 运行包含外层 SSE 寿命、多个模型请求、工具请求、检索通道以及数据库访问。每层超时控制的对象不同，需要端到端总预算，不能每个子步骤都完整使用外层剩余时长。

重试适合部分暂时性网络错误、限流等情况，但权限错误、确定的参数错误不应无限重试。通常考虑有限次数、退避、抖动和剩余总预算。超时只表示没按时获得结果，不证明服务端没有执行；写工具重试必须与幂等和状态查询配合。

项目的 Agent maxRetries、maxIters、SSE timeout 分别限制模型重试、循环次数与连接寿命，不能用一个数字替代三种预算。本篇不修改这些配置，也不假设重试已经覆盖每种外部错误。

## 44.7 ES、LightRAG、MCP、Python，是不是都由 Spring Boot 启动

Spring Boot 可以管理 Java 客户端、配置、接口和调用逻辑，但远端服务有自己的进程、数据和故障。LightRAG HTTP 服务不是 Java 内的知识图谱算法类；MCP 桥接负责发现与调用工具，并不把外部执行结果纳入 PG 本地事务；Python 评测器通过产品接口录制与评分，也不自动成为 Spring Bean。

排查跨服务问题时，理想记录 request/task、工具调用编号、目标服务、耗时和错误类别，并传播受控的 trace 上下文。日志写“调用失败”不够，还需要知道是哪次调用、哪个阶段、是否会重试。日志与 Trace 也不应随意保存密钥或完整敏感文本。

评测中尤其要分开产品运行时间与裁判评分时间；现有录制器聊天与检索旁路是两个请求，不能用旁路数据冒充同一 Agent 工具调用的完整证据。这些内容分别回接第 28、32～34 章。

## 44.8 三组完整模拟追问

以下是根据面经主题组合的教学对话，不声称某位面试官逐字问过这一整组。

### 第一组：从 Redis 使用问到可靠性

**问：Redis 在你的 Agent 项目中有什么作用？**

答：主链上负责同用户运行闸门和跨节点取消。历史和 Agent State 存 PG，活跃订阅在本机，Redis 保存资格与取消意图。

**追问：用什么数据结构，怎么加锁？**

答：Redisson RBucket 保存单值，原子 setIfAbsent 带 TTL；值包含本次 taskId 和会话，释放时 compareAndSet 校验 owner。它不是 RLock watchdog。

**追问：任务没结束，TTL 先到怎么办？**

答：过期不会停止旧任务，可能出现新旧运行重叠；比较 owner 只能避免误删新槽。更强写保护需要租约管理与下游版本/fencing 校验，当前未实现。

**追问：取消消息丢了怎么办？**

答：当前标记补偿注册前取消，Pub/Sub 不保证历史补发。已注册任务错过通知不能宣称一定取消。更强方案可增加安全点读取持久取消状态与重试，再通过本机 CAS 收敛重复通知。

### 第二组：从存储问到 SQL 与事务

**问：聊天记录怎么存？**

答：会话列表与消息分表，消息带 userId、conversationId、role、status，助手用 replyToMessageId 配对用户问题；AgentScope payload 单独保存，不拿展示轨迹冒充模型状态。

**追问：索引怎么建，联合索引缺一列还能用吗？**

答：会话按 userId 和 lastTime，消息索引按会话、用户和 createTime；实际按 id 排序不能默认被该索引满足。联合索引按字典序，缺中间列不意味着所有前缀能力消失，要区分定位范围和后续过滤，并看计划。

**追问：删除怎么保证一致？**

答：同库会话、消息和 State 删除在 PG 事务中，提交后协调取消与本机缓存。数据库事务不覆盖 Redis 和已经发送的 SSE；进一步保障旧运行不能回写，需要额外版本/墓碑设计。

**追问：外层事务调普通方法，异常会回滚吗？**

答：要看是否参与外层事务、异常是否传播与匹配回滚规则。普通方法没注解不意味着它的 SQL 不在事务里；自调用主要影响内层注解是否经过代理。

### 第三组：从 SSE 问到并发与故障定位

**问：如何流式返回？**

答：Spring MVC 创建 SseEmitter，订阅 Agent 事件，由 EventBridge 转成产品事件并缓存本轮轨迹，正常结束或取消时收尾。

**追问：完成和取消同时到来呢？**

答：每轮 RunHandle 的 CAS 竞争收尾资格，复合缓冲区操作用锁；连接 closed 与业务 settled 分开。CAS 控制次数，不保证数据库写入一定成功。

**追问：线程池里的异常外面能 catch 吗？**

答：不能仅靠提交线程的 try/catch 捕获未来异步异常，要在 Future/订阅回调观察。检索通道的异常与超时会被处理成空结果并记录日志，分析时要区分失败与真实无命中。

**追问：响应突然变慢，你看什么？**

答：先按 task/trace 分解接入、历史、检索、模型首字、工具、生成与落库耗时，再看对应线程池/连接池/数据库计划和外部限额。没有真实观测前，不直接把瓶颈归因于某组件。

## 44.9 学习优先级与掌握标准

第一优先级：能不用看稿讲完上述三组，每个概念能回到第 35～39 章一个真实流程。第二优先级：Redis 数据类型与失效、SQL 索引/MVCC、Spring 代理/事务、Java 线程池/可见性。第三优先级：被问到再扩展 JVM 类加载、复制故障、缓存进阶。

不要用“我负责了哪些高并发优化”替代“系统如何工作”。个人实际完成的改动和实验应另外准备证据；理解一个方案、提出一个方案、已经实现并验证，是三种不同面试材料。
