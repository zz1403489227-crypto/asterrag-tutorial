# 第 27 章：评估集——先定义什么叫好，再谈分数

评估集并不是随手找几十个问题。它是系统能力的一份具体说明：哪些问题应该能答，应该查什么资料，哪些地方应该澄清，哪些情况下根本不该搜索知识库。

上一章的 S2-01 看似只有一句问题，实际上背后带着一份评分标准。把这份标准设计好，后面才有可解释的分数。

## 27.1 给一道题配齐标准

用 S2-01 的真实字段，可以读出五个层次：

| 字段 | 本题的值或含义 | 为什么需要 |
|---|---|---|
| query_id / query | S2-01 / 手机屏幕尺寸与刷新率 | 对齐不同阶段的同一道题 |
| intent_l1 / intent_l2 | SUPPORT / S2_参数咨询 | 判断有没有识别问题类型 |
| requires_rag | true | 判断是否需要知识查询 |
| expected_doc_ids | PROD_PHONE_004 | 判断有没有找对资料 |
| ground_truth | 6.73 英寸、动态 1–120Hz | 判断知识是否齐全、答案是否正确 |

此外，数据里还有 difficulty、expected_answer_type、trap_type 等描述：这道题难在哪里，期待何种回答。它们帮助人理解题目构成，不等于每个字段都会自动产生一个评分器。

从教学角度，可以把一题理解为：

```text
给系统什么输入？       → 问题
期待它走什么方向？     → 意图、是否检索
期待它找到什么？       → 参考文档
期待它最后说清什么？   → 参考答案
这题想暴露哪种能力？   → 难度、场景、陷阱描述
```

这比“问题 + 标准答案”多了过程标准。它让评测能定位 RAG 的中间环节。

## 27.2 知识库和评估集不是同一种东西

知识库是系统做题时可以查的材料；评估集是考题和评分标准。

对这道手机题，商品文档里有参数、配件、注意事项等多种内容。用户只问尺寸和刷新率，参考答案就应围绕这两件事，而不是把整份商品说明书当成标准答案。

若参考答案要求系统复述所有产品资料，即使它正确回答了用户问题，也可能因为没有提到处理器、重量或充电功率而被判不完整。这是出题范围扩大，不是回答必然有问题。

所以正确顺序是：

```text
明确用户需求 → 找到支持材料 → 提炼必答事实与条件 → 编写参考答案
```

不是“从文档抄一大段，然后找一个差不多的问题”。

## 27.3 标准文档为什么分 must 和 nice

有些题不只需要一份文档。比如数据里的 S3-01 比较小米 14 与小米 14 Pro，标准文档包括 `PROD_PHONE_003` 和 `PROD_PHONE_004`。只拿到其中一份，通常不够做完整比较。

另外，选购推荐题还可能把选购指南列为必需，把具体产品详情列为补充。这就是两个集合：

- **must**：标注认为应当找到的核心材料，对应 expected_doc_ids。
- **nice**：可以丰富回答的补充材料，对应 expected_doc_ids_nice。

为什么要分开？假设一道题必须找到 A、B，补充材料是 C、D。检索结果拿到了 A、B，没有拿到 C、D。

按照核心目标看，任务需要的材料已经齐了；按照所有标注文档看，覆盖了 2/4。两者都可报告，但不能把后者直接解释为“关键知识缺了一半”。

作者同时提供 must Recall 和 inclusive Recall，就是为了保留这两个观察角度。具体计算在第 29 章展开。

还要认识到：标准文档集合是标注者定义的集合，不天然等于“全库所有能够回答问题的文档”。如果另一份材料也完整支持答案，文档指标可能偏低，而文本证据指标较好。此时应审视标注覆盖，而不是机械否定召回结果。

## 27.4 文档编号为什么不能随便用数据库 ID

同一份商品文档导入不同环境，数据库生成的内部 ID 可能不同。如果评估集绑定一个环境的内部数字 ID，换个环境后就可能明明找对了文档，比较编号时却全部不匹配。

项目使用类似 `PROD_PHONE_004` 的业务编号表达“这份资料是谁”，并通过映射兼容系统内部 ID。

```text
稳定业务编号 PROD_PHONE_004
         ↕ 环境映射或服务端名称还原
系统文档 ID
         ↕ 分块归属
chunk ID
```

这三个层次不应混用。文档是一整份商品资料；块是其中一段。块命中以后，要知道它属于哪份文档，才能算文档级 Hit 和 Recall；同时保留块文本，才能判断里面是否真有刷新率。

你不需要记映射函数名。要记住的是：**评测标准中的“正确对象”和系统返回对象，必须使用可以对齐的身份。**

## 27.5 为什么必须有“不该检索”的题

如果题库全部是查知识的题，一个“见到任何问题都搜索知识库”的系统可能看起来很好。但真实客服还会收到建议、抱怨和闲聊。

默认评估集里，F2-01 是用户希望 APP 增加深色模式；F3-01 是用户投诉客服态度。这两题都标为 requires_rag=false。它们考的是是否识别用户意图、采用合适回应，而不是能否找到一篇文档。

正例与反例共同定义行为边界：

```text
参数问答：需要知识 → 没召回就需要关注
功能建议：不需要知识 → 仍召回就可能是多余动作
```

注意“会说已记录反馈”和“真的创建了一张反馈工单”又是两件事。当前问答记录没有工具执行结果，不能仅从回答文字证明业务动作完成。这一点在 Agent 评测中尤其重要。

## 27.6 默认小集与全量集分别覆盖什么

在本篇锁定版本中，源码数据有两份：

| 数据文件 | 条数 | 一级意图构成 |
|---|---:|---|
| eval_set_v1.jsonl | 20 | SUPPORT 17、FEEDBACK 3 |
| eval_set_v1_all.jsonl | 150 | SUPPORT 125、FEEDBACK 15、CHAT 10 |

默认录制器读取第一份。它没有因为把 limit 调大就自动切换到第二份；limit 是截取数量，不是选择题库。

从原理上看，小集适合快速观察典型链路，全量集提供更广覆盖。但“更多”也不是唯一标准。如果增加的题只是同一个模板替换型号，就未必增加了多少新能力覆盖。

更有意义的覆盖轴包括：单事实与多事实、单文档与跨文档、直接词面与同义表达、条件判断与简单查值、应该检索与不该检索。项目已有场景、难度和陷阱描述可用于理解这些区分；现有核心指标主要按一级、二级意图聚合。

## 27.7 参考答案应是答案，不是给答题者的命令

比较以下两种写法：

```text
写法 A：应命中商品详情，回答屏幕尺寸和刷新率。
写法 B：屏幕尺寸为 6.73 英寸，刷新率为动态 1–120Hz。
```

A 适合作为出题说明。B 才能作为事实型参考答案。

为什么？后续裁判要把 reference 拆成事实，检查材料覆盖和回答一致性。如果 reference 只有“应回答某内容”，它没有告诉裁判那个内容到底是什么。拿元指令当答案，会让评分比较对象发生变化。

当前 S2-01 已经采用 B 这种完整答案；全量集仍能看到元指令形式的条目。因此不要把整个题库统一说成“标准答案都完善了”或“全是元指令”。要按实际样本看。

如果由你进一步维护题库，可以按以下原则处理：先从支持文档提炼事实；保留影响结论的条件；允许语义等价表达；把评分提示与参考答案分开；对政策、产品等版本相关内容记录资料版本。这里讲的是维护方法，不是声称本轮修改过题库。

## 27.8 为什么不能一边看考试题一边无限调参

假设你发现 S2-01 总是答漏刷新率，于是在提示词里加一句“遇到手机问题一定回答刷新率”。这题可能进步，但没有回答：别的问题会不会变差，系统是不是只记住了这套题？

更稳妥的评估设计是区分调试集与保留集：前者用于发现模式并改方案，后者用于判断方案能否迁移到未参与调试的问题。不同措辞但答案完全相同的近重复题，也应小心跨集合泄漏。

这是你在面试中可以提出的方法论。当前项目两份大小题库的存在，本身不等于已经做了严格的开发集/保留集隔离。
