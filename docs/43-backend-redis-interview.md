# 第 43 章：Redis 从数据结构到缓存、锁和消息，一条线讲明白

> 第二部分 · 基础追问。题库中 Redis 的问题跨越用途、结构、速度、过期、持久化、缓存一致性和锁。本章沿“存什么 → 怎么访问 → 怎么失效 → 怎么恢复 → 怎么协调”展开。

## 43.1 Redis 和关系数据库的本质差别是什么

Redis 提供以内存访问为核心的数据结构操作，适合快速状态访问、缓存和协调；关系数据库围绕表、约束、关系查询、事务和持久化管理数据。两者都能存数据、都可能有持久化，不能只回答“一个有磁盘，一个没磁盘”。

项目里，会话历史、Agent State 和长期记忆需要按业务关系查询和持久管理，存 PostgreSQL；用户运行资格和跨节点取消需要快速共享状态，用 Redis。分工从操作语义和生命周期出发，而不是所有“记忆”都放 Redis。

## 43.2 有几种数据结构？先答经典类型，再讲扩展

| 类型 | 怎样理解 | 典型操作/适用问题 |
|---|---|---|
| String | 一段字节或可操作的数值表示 | GET/SET/INCR；标记、计数、序列化对象 |
| Hash | 一个键下的多个 field-value | HGET/HSET；按字段访问属性 |
| List | 有顺序、可重复的元素序列 | LPUSH/RPOP；顺序缓冲与两端操作 |
| Set | 无序且去重的成员集合 | SADD/SISMEMBER；成员判断、集合运算 |
| Sorted Set / ZSet | 成员唯一，带排序分数 | ZADD/ZRANGE；排名、按时间/权重取范围 |
| Stream | 带条目编号的追加日志 | XADD/XREADGROUP；持久事件与消费进度 |

面试先把经典五种说清，再补 Streams；Bitmap、HyperLogLog、Geo 等可按场景说明，不必把所有新版本或扩展能力背成固定总数。[Redis 数据类型总览](https://redis.io/docs/latest/develop/data-types/)

**回到项目：** Agent 运行槽和 owner/cancel 标记使用 RBucket 保存单值；RTopic 是消息通道，不是“第六种保存聊天记录的 List”。Java 的 `RBucket<String>` 是客户端 API，值的编码交给客户端配置处理，不能只凭 Java 泛型推断 Redis 内部字节表示。

**Hash 和 String 存 JSON 怎么选？** 整体读写一个小对象，String 序列化简单；频繁独立修改多个属性，Hash 更贴近按字段访问。选择要考虑更新粒度、对象大小和过期管理，不能脱离当前版本承诺所有字段级行为。

## 43.3 “数据类型”和“底层编码”不是一回事

用户看到的是 Hash、ZSet 等逻辑类型；Redis 可以根据元素数量、大小和版本选择紧凑编码或更适合大集合的结构。紧凑布局省指针和分配开销，较大集合则需要兼顾查找与修改成本。

例如 ZSet 的常见大集合实现需要既能按成员定位，又能按 score 做有序范围访问，因此结合字典与跳表思路；跳表用多层稀疏链接加速有序定位，但不像 HNSW 在高维相似度空间里寻邻。不要见“多层图”就把两者讲成同一种算法。

以常见 Redis 7.x 的理解框架为例，可以先记这组对应关系，再针对明确版本补细节：

| 逻辑类型 | 常见底层思路 | 为什么这样组织 |
|---|---|---|
| String | 整数编码，或基于 SDS 的字符串表示 | 整数可紧凑保存；字符串记录长度并管理容量，不靠遍历寻找结尾 |
| Hash | 小对象可用 listpack，较大对象转哈希表 | 少量属性优先省空间，大量属性优先快速按 field 定位 |
| List | quicklist 组织紧凑节点，7.x 使用 listpack 等内部表示 | 在两端修改成本与内存局部性之间折中 |
| Set | 整数集合 intset、哈希表；7.2 起还有小集合 listpack 路径 | 根据元素类型和规模降低额外开销 |
| ZSet | 小集合紧凑表示，大集合常用字典加跳表 | 同时支持按成员找和按 score 排序找 |

这里不把阈值写成跨版本定律；小集合扩张到一定规模会转换编码，逻辑 API 不变。Redis 官方也按版本列出了 ziplist/listpack 与小 Set 编码差异。[内存与紧凑编码](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

## 43.4 为什么快，单线程为什么还能应对很多连接

主要因素是内存中的短操作、针对用途设计的数据结构、事件驱动 I/O 等。通常所说“单线程”强调核心命令执行路径，不代表 Redis 整个进程只有一个线程、持久化和网络处理永远没有后台并行。

事件循环在多个就绪连接间工作，不需要每个连接都常驻一个执行命令的线程；但一个命令执行得很久，仍可能影响其他请求。网络延迟、序列化、大结果集和内存带宽也会成为瓶颈，所以“所有 Redis 命令都是 O(1)”是错误的。

**项目回接：** 运行槽是小键小值、短条件操作，适合协调；若把整段大对话塞进一个大 value，每次修改都传输整段，则会增加网络与内存压力，不能因为数据库名是 Redis 就默认很快。

## 43.5 过期与淘汰为什么是两个问题

过期回答“这个键到时间了吗”；淘汰回答“内存预算不足时，优先让哪些键腾位置”。没到 TTL 的键也可能被淘汰，已过期键的物理清理也不等于所有键在同一瞬间被一个精确定时器删完。

Redis 通过访问时检查与主动过期检查等机制处理过期键。大量热点键同时失效，会把本来分散的重建请求挤在同一时刻；缓存场景可设计 TTL 抖动、分批预热、过期后的受控重建。[EXPIRE 官方说明](https://redis.io/docs/latest/commands/expire/)

淘汰策略包括面向所有键或仅有过期时间的键进行 LRU/LFU 等选择，以及 noeviction。LRU 关注最近使用，LFU 关注使用频度；Redis 使用近似策略而不是不计成本维护理想全局顺序。noeviction 会在内存压力下让相关写入失败，并不保证系统仍可无条件写入。[Redis 内存淘汰](https://redis.io/docs/latest/develop/reference/eviction/)

**项目追问：锁键被淘汰会怎样？** 正在运行的任务没结束，槽位却消失，新的任务可能进入。因此协调状态不能未经区分地放进“随便淘汰都没关系”的缓存策略；应讨论隔离内存预算、容量监控与故障策略。这是部署设计建议，不是当前源码已经配置了专门协调集群。

## 43.6 穿透、击穿、雪崩，用同一个知识助手举例

下面是缓存设计推演，不是项目已经实现的回答缓存。

**穿透：** 不断查询不存在的知识文档编号，缓存没有，数据库也没有，每次都直达数据库。可以校验输入、缓存短期空结果，或用布隆过滤器减少不可能存在的查询；空结果缓存需要处理新数据创建后的更新问题。布隆过滤器可能误判存在，不能把“可能存在”当成确定事实。

**击穿：** 一份热门报销制度缓存刚到期，大量请求同时回源。可以用 single-flight/互斥重建、提前刷新或旧值短暂兜底，让重建受控；互斥失败者是等待、返回旧值还是报忙，要明确。

**雪崩：** 大批键同时过期或 Redis 整体不可用，回源洪峰压垮数据库。除 TTL 错峰，还需要限流、降级、容量保护；Redis 宕机不是加随机 TTL 就能解决。

## 43.7 数据库更新后，缓存为什么会读到旧值

常见 Cache-Aside 读法是“先读缓存，未命中再读数据库并回填”。写时常讨论“先更新数据库，再删除缓存”，避免先删除后旧数据库值被立即回填，但它也不是无条件强一致。

一个经典竞争：读取者 A 先读到旧数据库值；写者 B 更新数据库并删除缓存；A 随后把旧值回填缓存。旧值再次出现。解决思路可能包括版本校验、受控重建、删除重试/可靠事件、对一致性窗口的业务约束。延时双删只是降低特定窗口的概率，延时怎么选、删除失败怎么补都需要解释。

**回到项目：** Redis Agent 闸门不是 PG 会话表的 Cache-Aside 副本，不能把这个缓存套路冒充当前会话一致性实现。项目真正在同步多个搜索副本的是向量/ES/图谱装饰器，应使用第 37 章的写入顺序与失败边界来回答。

## 43.8 RDB 和 AOF，重启时靠什么恢复

RDB 保存某个时间点的数据快照，恢复较直接，但最近快照之后的变化可能丢失。AOF 记录写操作，通过回放恢复；fsync 策略在性能与丢失窗口之间权衡，重写用于控制日志增长。后台快照/重写涉及资源开销，并非“后台执行所以对主服务绝无影响”。[Redis 持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

两者可组合使用，但持久化不等于主从强一致复制，也不等于故障切换绝不丢最近的锁状态。普通异步复制场景中，旧主确认写入后尚未复制就失败，新主可能没有那把锁，另一个客户端便取得资格。

对于项目运行槽，持久化能恢复的是“某个任务曾占着槽”这条数据，不是旧 JVM 的订阅对象。恢复出来的陈旧槽可能还要等 TTL；恢复与活跃任务的关系必须另行判断。

## 43.9 分布式锁四连问

**怎么加？** 用原子的“不存在才写入并带租期”表达资格，值带本次持有者身份。不能先 SETNX 再 EXPIRE，因为两者之间崩溃会留下无租期的键。

**怎么释放？** 原子比较 owner 再删除。不能直接 DEL，也不能分开 GET 与 DEL，避免旧任务删掉新任务的锁。

**过期了任务还没做完？** 租期不是任务生命的强制终止器。可以续租，但续租失败和长暂停仍需处理；严格的下游写保护可设计 fencing token。

**主从切换呢？** 异步复制可能丢锁状态，单节点锁方案的保障依赖故障假设。不要把“用了 Redisson”当作完整正确性证明，也不要简单宣称任何 Redis 锁都绝对不可靠而忽略业务容忍度。[Redis 分布式锁分析](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

回接项目时只需要准确说：RBucket 条件写入、taskId 所有权、CAS 删除、TTL；没有 RLock watchdog。

## 43.10 Lua 原子，是不是失败后全部回滚

Lua 在 Redis 中执行时，脚本相对于其他客户端命令具有原子执行边界，因此适合把检查与修改放在一起。它不等同于关系数据库事务的全套回滚语义：脚本运行时出错，不应假设之前的写入全部自动撤销；进程故障后的保存情况还取决于持久化与复制机制。

脚本也应短小，因为长时间执行会阻塞其他活动。逻辑原子性、故障恢复和业务补偿，要分开回答。[Redis Lua 执行模型](https://redis.io/docs/latest/develop/programmability/eval-intro/)

这对应面经中的“Lua 执行中 Redis 崩了怎么办”。先问清关心的是命令交错、已执行写入、磁盘恢复还是副本接管，再讨论对应机制，不要一句“Lua 原子，所以不会有问题”。

## 43.11 Pub/Sub、Stream 和列表，为什么不能互相冒充

Pub/Sub 是在线广播，订阅者漏掉的消息没有历史可补；Stream 是有条目和消费进度的日志结构，可配合消费组、确认、待处理检查等组织更可靠处理。可靠重投又会带来重复处理，需要业务幂等。List 可作为简单队列原料，但不自动具备这些确认与重投机制。[Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)

本项目取消用 RTopic 广播，加 cancel 键覆盖注册前的时序，不是持久任务日志。解释到这里，面试官追问“为什么不改成 Stream”，你就能从需求出发讨论可达性、复杂度与幂等，而不是只说消息中间件名字。

## 43.12 如果问“为什么不缓存模型答案”

这是面经中的 Agent 专项追问，下面是设计推演。先区分精确缓存与语义缓存：精确缓存依据确定键命中，语义缓存依据相似问题寻找可复用回答；语义相似不等于答案可互换。

知识答案依赖知识版本、模型/提示词版本、历史上下文、用户权限和检索作用域。缓存键或命中校验忽略这些条件，就可能返回过期制度或其他用户的材料。涉及工单创建等副作用，复用“成功答案”更不等于这次操作已经执行。

因此可优先考虑可重用的 embedding、稳定公共检索结果等合适层，明确版本与失效；对会话相关和有副作用的回答谨慎复用。评价缓存时同时看命中率、节省调用、陈旧答案比例和越权风险，而不是只报一个响应提速百分比。
