# 第 22 章：ES / BM25——用词语建立另一条找资料的路

> 上一章用向量表示语义、用 HNSW 加速近邻查找。本章换一个角度：不先问两段话的意思有多像，而先问它们提到了哪些相同的重要词语。

## 22.1 为什么找到“出差审批”还不够

继续前面的资料：林辰是远山科技的外包工程师，参与星河项目；星河负责人是周宁；外包差旅由项目负责人审批，正式员工差旅由直属经理审批。

用户问：“星河项目的外包工程师林辰出差，费用应该找谁审批？”

“正式员工找直属经理审批”和“外包人员找项目负责人审批”在语义上都与出差审批接近。但要答对，必须抓住“外包”和“星河项目”，不能只抓住一般主题。

关键词检索因此有自己的价值：对于项目名、人名、产品型号、制度编号等内容，词面重合是很直接的定位线索。语义检索能够跨越措辞差异，词面检索能够强调明确出现的词，两者看的是不同信息。

先不要急着讨论融合。我们先完整建立这条词面检索链。

## 22.2 从全文扫描到倒排索引

假设我们有四段文字：

```text
D1：林辰是远山科技的外包工程师，目前参与星河项目。
D2：星河项目的负责人是周宁，远山科技提供研发支持。
D3：外包人员的项目差旅费用，由所在项目负责人审批。
D4：正式员工的差旅费用，由直属经理审批。
```

最直接的关键词搜索，是对每段文字检查是否包含某些词。但资料多起来以后，每次查词仍要扫描大量正文。

倒排索引把组织方向反过来：不是只保存“文档里有哪些词”，还建立“这个词出现在哪些文档里”。为理解结构，先把词语简化成下面这样：

```text
林辰       → D1
远山科技   → D1、D2
星河项目   → D1、D2
外包       → D1、D3
负责人     → D2、D3
审批       → D3、D4
```

右边叫倒排列表。它不仅可以记录文档 ID，还可记录词频等信息，为后面的相关性打分提供依据。

现在搜索“外包 审批”，检索器从“外包”的列表取到 D1、D3，从“审批”的列表取到 D3、D4，再根据查询规则组织候选。它不用为了找到这两个词，先读完每一篇不相关的长文。

**倒排索引解决的是“哪些文档可能相关”，而不是“哪篇最值得排第一”。** 找到候选之后，还需要排序规则。这就是 BM25 出场的位置。

## 22.3 中文文本必须先解决“词是什么”

英文通常有空格，中文的“星河项目外包人员差旅审批”却是一串连续字符。搜索引擎需要先分析文本，将它转换成可检索的词项。

写入阶段对文档做分析；查询阶段也对问题做分析。两边产生的词项能够对应，查询才有机会在倒排表里找到目标。

```text
写入：原文 → 分析 / 分词 → 词项 → 倒排列表
查询：问题 → 分析 / 分词 → 词项 → 查找倒排列表
```

如果项目名称被不合适地切分，或者查询用的是索引没有覆盖的别称，后面的打分算法再好，也可能找不到理想候选。因此，中文关键词检索并不是一句“上 BM25”就结束，分词与领域词汇也是检索设计的一部分。

在 Elasticsearch 中，`text` 字段会经过这种分析；`keyword` 字段通常保留整体值，适合筛选库名、状态码等结构化信息。[Elasticsearch 字段说明](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/text)

这解释了一个看似反常的现象：项目的关键词检索主要搜索 `content` 的 `text` 字段；知识库名则映射为 `keyword`，用来回答“只搜索哪几个库”。

## 22.4 BM25 的第一个问题：词出现几次才算重要

假设两段文字都包含“外包”：一段出现一次，另一段出现两次。其他条件相同时，多次出现通常提供更强的词面线索。

但是，出现一百次不应该比出现一次有用一百倍。否则重复模板、关键词堆砌和冗长文档容易占据前排。

BM25 因此采用词频饱和：刚开始多出现一次的收益比较明显，继续重复的边际收益逐渐变小。可以想象成一条上升后逐渐变平的曲线。

为了看清这一点，暂时假设片段长度恰好等于平均长度，并取 `k1=1.2` 做计算：

| 某个查询词的出现次数 | 对应词频部分的贡献 |
|---|---:|
| 1 次 | 1.00 |
| 2 次 | 约 1.38 |
| 10 次 | 约 1.96 |

从 1 次到 10 次，并没有增加到十倍。BM25 在表达的是“多出现值得加分，但不能无限靠重复取胜”。

## 22.5 第二个问题：所有词一样有区分度吗

在企业知识库中，“规定”“项目”可能到处出现，“星河”“林辰”却只在少数材料中出现。

如果一个词几乎每篇文档都有，它很难帮助我们区分资料。相反，较少见的词一旦匹配，往往更能缩小范围。逆文档频率 IDF 就在表达这个差别。

注意“词频”和“文档频率”的区别：

- 词频 TF：这个词在当前片段里出现了几次。
- 文档频率 DF：整个被索引语料中，有多少篇文档含这个词。
- 逆文档频率 IDF：将 DF 转换成区分度权重，越普遍的词通常权重越低。

“林辰”在一段话里出现十遍，影响 TF；它在全库一万篇材料里都出现，影响 DF。前者是局部统计，后者是语料统计，不是同一个数字。

## 22.6 第三个问题：长文档是不是天然占便宜

长片段更容易碰到查询词。一本二十页的员工手册可能同时包含“外包”“审批”“差旅”，但这几个词分散在不同章节，未必共同回答当前问题。

BM25 会考虑片段长度相对于平均长度的比例。在其他条件相同时，同样出现两次查询词，短片段往往更集中，长片段的词频证据则需要适当折算。

这里不是“短的一定比长的好”，而是对长文档天然更多的匹配机会做校正。参数 `b` 控制长度校正的程度；`b=0` 时不做这部分校正。

这和 RAG 分块产生了直接联系：ES 中被评分的文档，在本项目里是一个 chunk，而不一定是一整份原文件。分块长度分布改变了，词频和长度统计也会跟着改变。因此，分块策略不只影响 Embedding，也会影响 BM25 的排序行为。

## 22.7 把三种因素放进一条公式

理解完词频、区分度和长度，再看常见的 BM25 形式就容易了：

```text
score(q, d) = Σ IDF(t) ×
              f(t,d) × (k1 + 1)
              ─────────────────────────────────────────
              f(t,d) + k1 × (1 - b + b × |d| / avgdl)
```

求和遍历查询中的词项。`f(t,d)` 是词 t 在片段 d 中的次数；`|d|` 是片段长度；`avgdl` 是平均片段长度。

读公式时只抓三个位置：

1. 前面的 IDF 决定这个词有没有区分度。
2. 分子和分母中的 f 共同制造词频饱和。
3. 分母中的长度比例调整长短片段带来的差异。

Lucene 的 BM25 使用正值 IDF 形式 `log(1 + (N - n + 0.5)/(n + 0.5))`，其中 n 是包含该词的文档数；具体打分实现还有字段统计与编码细节。上述公式用来理解三个因素如何配合，不需要把它当作本项目手写的 Java 算法。[Lucene BM25 说明](https://lucene.apache.org/core/9_12_1/core/org/apache/lucene/search/similarities/BM25Similarity.html)

项目将评分交给 ES，使用默认 BM25 similarity。[Elasticsearch similarity 说明](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

## 22.8 一次查询怎样走完整条链

现在查询：“星河项目的外包工程师林辰出差，费用应该找谁审批？”

首先，查询分析器提取可检索词项。接着，搜索引擎使用倒排列表寻找含相关词项的片段，并限制知识库范围。

此时候选可能很不一样：D1 包含林辰、外包和星河项目，擅长定位人员身份；D2 能定位项目负责人；D3 描述审批规则；D4 虽然也提到差旅审批，却对应正式员工。

BM25 为匹配到的词项计算贡献并汇总，给候选排序。它可能强化 D1 的专名线索，也可能强化 D3 的制度线索。这还不是最终结论，因为正确回答需要综合“身份”“角色”和“规则”。

```text
问题文本
  → 分词，得到查询词项
  → 查倒排列表，收集可能匹配的片段
  → 限定知识库范围
  → 根据词频、IDF、长度计算 BM25 分数
  → 排序，返回前若干条候选
```

倒排索引负责高效定位，BM25 负责词面排序。两者合作，才构成完整的关键词检索过程。

## 22.9 为什么称它为“稀疏检索”

假设词表有十万个词。用一个十万维的空间表示文本，每一维对应一个词，大多数短片段只涉及其中几十个词，其他维度都是零。这种表示天然稀疏。

倒排索引正好适合这种结构：没有出现的词，不必为每个文档都存一份零值，而是记录真正出现过的词与文档关系。

因此，BM25 常被归入词法或稀疏检索。它与稠密 Embedding 的核心差别是：前者的维度对应词项，匹配依赖词面；后者由模型学习一组连续特征，能够表示不同措辞之间的语义接近。

回到项目，实际接入的是 ES 文本索引与 BM25，而不是另一套独立的稀疏向量编码模型。记住这个落点即可，不必让术语争论盖过检索过程。

## 22.10 项目如何把关键词路接到原来的入库流程

项目不会为了 BM25 重新设计整套文档解析。解析和分块仍然共用，同一段文本产生两个用途：

```text
同一个 chunk
  ├─ 生成 Embedding → 写向量库 → 供 HNSW 近邻检索
  └─ 保存正文和归属 → 写 ES    → 供倒排 / BM25 检索
```

ES 保存正文、知识库名、文档 ID 和片段序号。正文映射为 `text`，库名等身份字段用于过滤和关联；ES 这条路径不需要收到片段的稠密向量。

默认分析配置使用 `ik_max_word` 写入分析、`ik_smart` 查询分析。查询对正文执行 `match`，取得 ES 分数，再转成与向量路相同的候选对象，交给后续融合。

这条 ES/BM25 路径是可选能力，默认关闭。是否启用是项目配置问题；它的检索原理就是本章刚走过的“分析—倒排定位—BM25 排序”。

## 22.11 为什么它和向量路应该合作

如果用户把“审批”换成“找谁签字”，语义检索可能更容易跨越措辞变化。如果问题包含精确项目名或制度编号，词面检索又能提供直接定位线索。

所以两路不是新旧替代关系。可以把它们理解为两位查资料的人：一位根据意思找，另一位根据重要词找。各自带回不同候选，再由统一流程比较和整理。

但到这里，我们仍主要在找一段段文本。林辰的身份、星河的负责人和差旅的审批规则散在不同地方，是否还能把这些知识之间的关系直接组织起来？下一章由此进入知识图谱。
